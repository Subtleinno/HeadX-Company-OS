# PLAYBOOK：品牌素材交付

版本：v1.0 | 2026-11-03
對應主方案：`SOLUTION_SPACE.md` 第五節「11 → 10 → 7 → 18」
用途：這是第一個 playbook。將來每解決一類問題，就固化成一個 playbook，同類問題直接調用。

---

## 一、這個 playbook 解決什麼

| 項目 | 內容 |
|---|---|
| 解決 | P1 規則不可執行、P3 錯誤後才發現、P2 執行無法分工 |
| 觸發 | 有一個品牌專案要做一份交付物（影片／網站頁／排版） |
| 頻率 | 每月 2 至 6 次 |
| 成功判準 | O1 交付 ≤ 5 工作日、O2 一致性 ≥ 4、O5 攔截 ≥ 90%、O6 缺口 100% 記錄 |
| 人類批准點 | **兩個**：① 方向選定 ② 交付前放行 |

---

## 二、流程（端到端）

```
① 讀品牌規則            [工具] 讀 catalog 與 tokens
        ↓
② 定專案                [人＋AI] 選渠道、子渠道、格式、策略
        ↓  人類批准點 1（方向）
③ 補知識與缺口          [AI] 只引用已勾選的事實；缺的進 gaps
        ↓
④ 生成第一稿            [AI] 按策略與 tokens 生成
        ↓
⑤ 自動檢查              [工具] 跑 lint；fail 就回 ④
        ↓
⑥ 人審（美與策略）       [人] 只看 guidance 類與整體感
        ↓
⑦ 缺口轉 Needs          [工具] 非阻塞缺口 → 工單；阻塞缺口 → 狀態 need
        ↓
⑧ 人類批准放行           [人] 人類批准點 2（交付）
        ↓
⑨ 交付並記錄            [工具] 寫入 delivered_at、檢查結果、缺口清單
```

---

## 三、逐步規格

### ① 讀品牌規則

| 項目 | 內容 |
|---|---|
| 負責 | 工具（`parts/design/src/loader.mjs`） |
| 輸入 | 品牌 id |
| 輸出 | 可用策略清單（按渠道過濾）、品牌 tokens |
| 驗收 | 缺 tokens 要報錯並指出缺哪個；策略清單不可為空 |
| 例外 | 品牌未建立 → 停止，提示先建品牌 |

### ② 定專案

| 項目 | 內容 |
|---|---|
| 負責 | 人（老闆）選，AI 提供候選 |
| 輸入 | 渠道、子渠道、格式、策略 |
| 輸出 | 專案記錄（`ref_no`、`status: draft`） |
| 驗收 | 策略必須在該渠道的可用清單內（`scope` 過濾） |
| **人類批准點 1** | **方向由人選定。AI 可以建議，不可以自己定。** |
| 例外 | 沒有合適策略 → 開 issue 討論要不要新增策略，不要硬選 |

### ③ 補知識與缺口

| 項目 | 內容 |
|---|---|
| 負責 | AI |
| 輸入 | 專案意圖 |
| 輸出 | `knowledge`（已勾選事實）與 `gaps`（缺口） |
| 驗收 | **每一句具體陳述都要能指向一條 knowledge**；指不到的進 gaps |
| 硬規則 | 不准用「無來源的形容詞」填滿內容 |
| 例外 | 阻塞缺口 → 狀態轉 `need`，流程停在此處等人 |

### ④ 生成第一稿

| 項目 | 內容 |
|---|---|
| 負責 | AI（渲染／圖像／文案） |
| 輸入 | 策略、tokens、knowledge、意圖 |
| 輸出 | 交付物檔案 |
| 驗收 | 尺寸與格式符合 catalog 的 format 規格 |
| 例外 | 生成失敗要保留日誌並回報，不准靜靜失敗 |

### ⑤ 自動檢查

| 項目 | 內容 |
|---|---|
| 負責 | 工具（`runner.mjs`） |
| 輸入 | 交付物檔案 |
| 輸出 | 逐條 pass / fail / skip |
| 驗收 | **有 fail 就不可進入 ⑥**；skip 要在報告中列明原因 |
| 例外 | 檢查器本身出錯 → 當作 fail（不可當作 pass） |

### ⑥ 人審

| 項目 | 內容 |
|---|---|
| 負責 | 人（老闆） |
| 只看 | `guidance` 類條款、整體是否符合策略、有無明顯不當 |
| 不看 | `lint` 已覆蓋的東西（不再重複看，省時間） |
| 輸出 | 通過 / 退回（附一句原因） |

### ⑦ 缺口轉 Needs

| 項目 | 內容 |
|---|---|
| 負責 | 工具（`gaps.mjs`） |
| 輸出 | Needs 工單，**必填 `attempted`** |
| 驗收 | 同一缺口不重複開單 |
| 例外 | 缺口缺 `because` → 拒絕開單並要求補 |

### ⑧ 人類批准放行（批准點 2）

| 項目 | 內容 |
|---|---|
| 負責 | 人 |
| 為什麼要有第二個點 | ① 是「方向對不對」，⑧ 是「可以交出去嗎」。兩者判斷的東西不同 |
| 不可自動 | **不准有任何「低風險自動放行」開關** |
| 輸出 | 批准記錄（誰、何時、基於哪個檢查結果） |

### ⑨ 交付並記錄

| 項目 | 內容 |
|---|---|
| 負責 | 工具 |
| 記錄 | `delivered_at`、檢查結果全文、缺口清單、批准記錄 |
| 驗收 | 記錄不可事後修改（append-only） |

## 四、例外與升級路徑

| 情況 | 做法 |
|---|---|
| 檢查一直 fail，改不到 | 回到 ② 重選策略（不是放寬門檻） |
| 策略清單沒有合適的 | 開 issue，人決定要不要新增策略 |
| 品牌 tokens 缺項 | 停，先補 tokens |
| 生成質素一直不到 O2 ≥ 4 | 觸發備援方案（模板庫） |
| 老闆沒時間審 | **不可跳過**，只能延後交付 |

**關鍵：所有「卡住」的情況，都不准用放寬檢查來解決。**

## 五、每個步驟對應哪個指標

| 步驟 | 指標 |
|---|---|
| ① ② | O7 重複解釋次數 |
| ③ ⑦ | O6 缺口記錄率 |
| ④ ⑤ | O5 錯誤攔截率 |
| ⑥ | O2 品牌一致性 |
| ⑧ ⑨ | O4 老闆時間 |
| 全程 | O1 交付時間、O3 修改輪數 |

## 六、這個 playbook 何時要改

| 觸發 | 回到哪一步 |
|---|---|
| O5 攔截率上不去 | 檢查 `PROBLEM.md`：被退回的原因是否真的機械可驗（假設 A4） |
| O2 一直低 | 檢查策略是否寫得夠具體（回 `SOLUTION_SPACE.md` 階段 11） |
| O1 沒改善 | 檢查是不是「老闆時間」只是搬去了 ⑥ 與 ⑧（假成功） |
| 出現更便宜的解法 | 回 `SOLUTION_SPACE.md` 重新評分 |

## 七、下一個 playbook 會是什麼

按 `SOLUTION_SPACE.md` 次序，做完這個之後，同一個形狀可以直接套：

| 候選 playbook | 觸發 | 規模 |
|---|---|---|
| 新品牌建立識別 | 每季 | 一次性 |
| 網站頁交付 | 每月 | 週期性 |
| 對外發佈（L3） | 事件驅動 | 需批准 |
| 缺口派工與驗收 | 事件驅動 | 人機協作 |

**每一個都是同一個四件套，只是換目錄與條款。**
