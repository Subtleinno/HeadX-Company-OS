## 0. 一句話

一套你自己擁有、裝在自己公司機器上的系統：把公司的**策略、記憶、產出**集中在同一處，
AI agent 在裡面做大部分工作，人只補 agent 做不到的部分，你只落策略、看全貌。

不是買 ERP，也不是租 SaaS。是**你開公司用的基建**。不賣，只按客客製——第一個客戶是你自己的生意。

## 1. 起點：為甚麼不是 ERP

傳統 ERP 的隱含假設是「人是主要執行者，軟件是記錄工具」。所有設計由此而來：表單、審批流、權限樹、月結。

這套的假設相反：

> **agent 是主要執行者，人是判斷者與補位者。**

由此推出三條，所有設計決定都要通過這三條：

1. **軟件要為 agent 而設。** 接口是一等公民，畫面是給人看結果與補位用的。不是「有 API 的 ERP」，是「有畫面的 agent 平台」。
2. **人只在 agent 做唔到的地方出現。** 所以「做唔到」必須是一條正式、可見、可追的流程（Needs），而不是錯誤訊息或靜靜降級。
3. **預設不加閘。** 判斷交給人看成品：不夠好就叫 agent 再做一次。加閘只會令系統變慢、變複雜，而判斷質素不會因此提高。

第 3 條要講清楚：**「唔加閘」是預設值，不是架構禁令。** 你自己逐項決定哪一項要批核。
系統不會替你決定「這件事要人批」，也不會替你決定「這件事不用批」。

## 2. 七個原則（不可違反）

| # | 原則 | 意思 | 做錯會變成 |
|---|---|---|---|
| 1 | **預設無閘** | 不預設 approval gate；由你逐項決定哪一項要批 | 傳統 workflow 系統，agent 卡在半途 |
| 2 | **一個 app 一個工作台** | 一個 app＝同一批人、同一節奏、同一組核心物件；清單對一間公司固定，你管註冊 | 無止境增生的插件市場 |
| 3 | **策略由你寫，agent 只揀同跟** | 策略不是 AI 生成，是你手動加入 | agent 自己發明方向，越走越遠 |
| 4 | **成品留在出身的 app** | Marketing 做的圖與片留在 Marketing 的 Create，不回流中央 | 中央素材庫變成第二個要維護的倉 |
| 5 | **平台殼只做四件事** | 切換、身份、註冊、事件 | 一個越長越大的怪物 |
| 6 | **可配置優於寫死** | 同一套 OS 會裝在不同公司；業務語義（計量方式、批核項、科目、職級）一律是設定，不是寫死在程式裡 | 一套只賣得一間公司的定製品 |
| 7 | **app 由規格編譯，不由 agent 自由創作** | 缺少的 app 由你一句話起，Forge 編譯出一份 App Spec；生成物只能寫 app 層，改不到框架 | 無止境增生、沒人收的孤兒 app |

原則 5 值得展開：**平台殼（Frame）不是資料總管。**
它不知道一個 marketing project 裡面有幾張圖，它只知道「這個 app 存在、健康、有幾多活躍 project、有幾多未完成 Needs」。
所有業務資料的擁有者，永遠是部門 app。

原則 7 回答原則 6 留下的洞：**如果新公司需要一個原始碼沒有的 app 怎麼辦？**
答案是 App Forge：你講一句 → 它用十二條變化軸問清 → 產出一頁 App Spec → 由 App Kit 編譯成可註冊的 app。
**加一個部門不是改框架，是加一份 spec。**

## 3. 三層結構，一條硬邊界

```
你 → Boss Portal（總覽只讀；設定裡的帳戶頁可寫身份）
        ↑ 總覽不插手 project。帳戶與部門歸屬是身份，放在設定。
部門 app（Marketing、Sales、Operations、Finance、HR…）
        ↑ 每個 app 擁有自己的資料與產出
平台殼（切換 app、身份權限、註冊表、事件日誌）
        ↑
Postgres（狀態與紀錄）＋ MinIO（檔案與成品）
```

**一條硬邊界：成品留在出身的 app，不回流中央。**
中央一旦有一份可寫的副本，就會出現兩個真相，之後沒人敢改。

同一條原則用四次，形式不同：

| 場景 | master 在哪 | 其餘是什麼 |
|---|---|---|
| 成品 | 出身的 app 的 Create | Boss Portal 只顯示件數與狀態 |
| 跨 app 取數 | 擁有資料那個 app | 經 MCP 問它，不 join 它的表 |
| 多據點 | 最低那一層（Site） | Hub 只收摘要，永不存 master |
| 電商渠道 | 商品在 ERP、庫存在 Operations | 渠道是投影與命令，不是第六個 master |

## 4. 十二個物件

整份構思壓縮成十二個物件。之後資料庫的 schema 就是這張表。

| 物件 | 一句定義 | 擁有者 |
|---|---|---|
| **Platform Shell** | 外殼：app 切換、身份、註冊表、事件日誌 | 公司 |
| **Department App** | 一個部門的完整工作空間，含自己的資料、畫面、專案 | 該部門（你管註冊／升級） |
| **App Spec** | 一個部門 app 的規格。**app 由它編譯出來** | 你（Forge 起草） |
| **Project** | 一件工作。由同事一句話開始，agent 建立 | 部門 app |
| **Create** | app 內存放與編輯產出的地方；Project 的產出歸屬 | 部門 app |
| **Needs** | agent 做唔到時開的工單，指名要甚麼、為哪個 project、哪個位置 | 部門 app（指派給同事） |
| **Strategy Doc** | 你手寫的策略／SOP；多份、多點分佈，agent 按任務揀 | 你 |
| **Preference Doc** | 每位同事的偏好檔；你可讀寫、agent 可讀、同事不可讀寫 | 你 |
| **Asset** | 四類：品牌（識別／模板）、知識（文件）、素材（相／片／聲）、圖表模板 | 部門 app |
| **Render Job** | 一次出圖／出片的請求與結果 | 部門 app ＋ 出圖服務 |
| **Automation** | **由 agent 撰寫、可 diff 可回滾的程式**；把重複路徑拿走，換成確定性 | 部門 app（平台級能力） |
| **Company Profile** | 這間公司的設定：專案邊界、權限、批核項、開哪些 app | 你 |

`App Spec` 與 `Department App` 的關係，正如 **HTML 稿與出爐成品的關係**：前者是真相，後者是導出物。
同一個心智模型用了兩次，不是巧合。

> 命名註：`Needs` 這個名在 2026 年已至少被三個產品使用。功能照舊，名字待定。

**框架只認六條不變量**：物件與擁有權、三層組織、autonomy、Needs 兩型、Registry 四 shape、事件格式。
這六條之外，任何「我們公司是這樣做的」都不進框架。這條紀律決定三年後它是薄殼還是一團。

## 5. 角色

四種，刻意不做第五種。

| | Boss（你） | Staff（同事） | AI Agent | External（外判） |
|---|---|---|---|---|
| **Boss Portal** | 全部可見 | 只見自己的 Needs 與 project | 唯讀自己的 project 狀態 | 不可見 |
| **部門 app** | 全部可見 | 自己部門 | 經 MCP，按 project 授權 | 不可見（只有 Needs inbox） |
| **Strategy Doc** | 讀＋寫 | 讀 | 讀 | 只讀被引用的段落 |
| **Preference Doc** | 讀＋寫（全部） | **不可讀、不可寫** | 讀（只讀當前任務那位） | 不可讀 |
| **Needs** | 看全部 | 看＋做＋上載 | 開立＋驗收（吸收結果） | 只看指派給自己的 |

兩點是刻意的：

- **Preference Doc 對同事隱藏。** 理由是避免同事「為 AI 寫履歷」而扭曲真實工作習慣。業界主流相反，這個取捨要自覺承擔。
- **你對部門 app 的權力是「註冊與升級」，不是「管 project」。** 你可以看任何 project，但不在 Portal 內指派、改期、改狀態。

## 5.1 登入落點與帳戶

登入之後去工作地，不去「我的 Apps」。

- 老闆去 Boss Portal。老闆不屬於任何部門。
- 員工去所屬部門 app。現在只有 Marketing Design。一人一個部門。
- 外判不走這條，只有自己的 Needs。
- 未指派可以登入，但進不了部門。畫面寫「未獲指派部門，請聯絡老闆」。
- 員工可以有自己的一頁，但現在不設計，也不是落點。

建立帳戶、停用登入、重設密碼、所屬部門，放在 Boss Portal 的同一頁「帳戶」。部門是欄位。建立時就要選部門。老闆可以重設別人的密碼。員工改自己的密碼不在這頁。停用是不能登入，不是離職。

現在不開 HR，也不另開員工 app。HR 以後才開，時機是要計糧、簽合約、或處理假期。HR 管僱傭，不管登入。總覽仍然不指派、不改期、不改 project。

這一節與「Portal 只讀」衝突時，以這一節為準：總覽只讀，帳戶設定可寫。

## 6. 一個請求怎樣走完

起點永遠一樣：**同事對 agent 講一句人話**（例：「做一個介紹品牌的 IG Carousel」）。

agent 依次做六件事：

1. 接入 OS，判斷屬於哪個部門 → 路由到該 app
2. 在該 app 開一個 Project
3. **揀策略**：按任務性質，從多份策略文件揀出最合適那幾份（不是一份）
4. **四庫取材**：按策略指示去品牌、知識、素材、圖表模板揀料
5. **組稿**：把選中的東西編譯成一份 HTML composition（含品牌色字、素材引用、分頁、文案）
6. **判斷齊料與否** → 兩條路

**路 A：齊料**

```
組好 HTML 稿 → 直接 render → 成品存入該 app 的 Create
→ 同事開 Create 睇 → 收貨，或者叫 agent 再改（回到第 3 步，不是重新開始）
```

**路 B：缺料**

```
agent 知道自己缺甚麼 → 開 Needs（一張或多張）放入 project
→ Project 存為「半成品」（稿已存在，只是有位置未填）
→ 同事收到需求 → 製作 → 上載
→ agent 自動標籤＋描述 → 存入素材庫（日後可重用）＋ 即時填入本 project 的空位
→ 所有 Needs 關閉 → 回到路 A
```

關鍵：**路 B 不是失敗，是正常路徑。** 半成品是一個合法狀態，不是錯誤狀態。

兩條路共用同一個物件：HTML composition。
半成品＝帶空位的稿；成品＝空位填好之後 render 出來的結果。不需要兩套資料結構，也不需要「匯入」步驟。

## 7. Needs 閉環（整套東西最值錢的部分）

為甚麼值錢：業界多數假設 agent 要嘛做完、要嘛靜靜降級。
把「做唔到」變成可見、可派工、可沉澱成重用資產的正式流程——這是真正的人機協作，而且最難被抄。

**一張 Needs 必須帶六樣：**

1. 屬於哪個 Project
2. 對應哪個位置（稿內的位置）
3. 要甚麼：類型、尺寸、比例、格式、數量
4. 為甚麼要（引用哪份策略的哪一段，讓同事明白脈絡，不是盲做）
5. 何時要
6. 狀態與歷史（誰開、誰做、何時上載、agent 何時吸收）

**兩種型別：**

| 型 | 要人交出 | agent 的責任 |
|---|---|---|
| `deliverable` | 一樣東西（檔案、相片、資料） | 講清規格與用途 |
| `decision` | 一個判斷（授權、簽名、選哪個） | **必須先做一次並附建議**，不是把問題原封丟給你 |

**狀態流轉：**

```
開立 → 待認領 → 進行中 → 已上載 → 已吸收 → 關閉
                    ↘ 需要補件（回到進行中）
```

「已吸收」是關鍵一步：**上載不等於完成**，要等 agent 把檔案標籤、描述、入庫、填回 project，才算閉環。

**刻意不做：** 不上載後等人覆核標籤、不設多層驗收。
標籤錯，下次檢索就會揀錯料，agent 產出變差，同事自然會叫它再做——由結果反饋，不由流程攔截。

## 8. 策略層：多點分佈，不是一份總部文件

這裡最容易做錯。策略不是一份「公司策略」放在總部，而是**散落在系統很多位置的多份文件**：

| 層 | 例子 | 管甚麼 |
|---|---|---|
| 品牌層 | 「Moonic 品牌語氣指引」 | 用色、字體、語氣、禁用詞 |
| 渠道層 | 「IG Carousel 製作規範」 | 尺寸、頁數、首頁規則、CTA 位置 |
| 格式層 | 「簡報頁編排規則」 | 版面、資訊密度 |
| 步驟層 | 「品牌介紹類內容的敘事順序」 | 先講甚麼、後講甚麼 |
| 範例層 | 「上次這個 campaign 的做法」 | 具體可模仿的例子 |

**agent 揀策略是一個 routing 問題，不是一次搜尋。**
它要先判斷任務類型，再逐層揀：品牌層幾乎必讀，渠道層看產出格式，步驟層看任務目的。揀錯會直接反映在成品上。

**你只做兩件事：加、改。** 沒有審批流、沒有發布流程、沒有生效日。加了就即時生效。

**唯一保留（零成本）：** 每個 Project 靜靜記低用了哪幾份策略、哪個版本。
不顯示、不彈窗、不阻塞。目的是幾個月後你問「為甚麼這個產出是這樣」時，有得查。

## 9. 公司層、品牌層，與「誰可以從網絡上碰到它」

這一節回答你 2026-11-11 問的：有些可以公開（Cloudflare tunnel），有些只能內網或 VPN；有些是公司層，有些是品牌層。

**方向對，但這是兩個不同的軸，不可以合成一個開關。**（C82）

### 軸一：Scope（我喺邊個上下文工作、寫入落邊）

| 層 | 是甚麼 | 有甚麼 |
|---|---|---|
| **公司層** | 整間公司 | 財務、人事、Boss Portal、客戶與產品主檔 |
| **品牌層** | 一個品牌的工作上下文 | 該品牌的語氣、素材、創作、渠道 |

公司層的資料**不屬於任何品牌**。
所以若「公開」係品牌 workspace 的屬性，就會出現：品牌 A 設成公開，同事喺品牌 A 頁面按入財務，**財務忽然公開了**——沒有人做過這個決定，但資料已經出去了。

### 軸二：Reachability（呢個請求由邊道門入嚟）

三層，**只能向下收窄，永遠不能向上放寬**：

| 層 | 內容 | 誰決定 | 現況 |
|---|---|---|---|
| 1 硬上限 | 每個 app 宣告 `internal`／`partner`／`customer` | 寫在程式庫，改要一個 PR | **已實作**，有真 HTTP 測試 |
| 2 部署形狀 | 今次開幾道門、tunnel 指去邊 | 部署時決定 | 只有「內部網絡」一道門 |
| 3 顯示與意圖 | 你而家喺邊道門、這個 app 准唔准由呢道門入 | 畫面誠實呈現 | 權限不足已有全螢幕說明；「對外存取」頁排在隊列之後 |

一句：**程式庫講「最多可以去到邊」，部署講「今次開幾道門」，畫面只講「你而家喺邊」。**
任何一層都不可以由畫面直接提高上限。

### 組織層級：Site / Tenant / Group

| 層 | 是甚麼 | 擁有甚麼 |
|---|---|---|
| **Site** | 一個地點、一個安裝；斷網仍可運作 | 庫存、預約、排班、門市現金 |
| **Tenant** | 一個法律實體 | 客戶、產品與價目、科目表、員工、薪酬 |
| **Group** | 你的持有結構 | 只有投影與事件，**永不存 master** |

**硬規則：事件永遠向上流，master 永遠在最低那一層。** Hub 只收摘要，不看明細；Hub 死了各 site 照常運作。
第一版：**一個 Tenant 一個 Site**。多店（一公司多店）留到之後。

## 11. 刻意不做、與暫時不做

**刻意不做（設計決定，不是未做）：**

- 不做 marketplace／雙邊平台：需要「買方」與「賣方」兩個抽象，會牽動 Sales 全部。但做渠道接駁（Shopify／WooCommerce 是 Commerce 的渠道，不是要我們自建前台）。
- 不做中央素材庫：素材屬於部門 app。
- 不做 workflow engine：預設沒有審批鏈。
- 不做全站搜尋、不做深色模式、不用紫色漸層、不用 emoji（C63、C65）。
- 不做「無 bug」的承諾：可承諾的是「15 分鐘內回滾、RPO ≤ 1 小時、單一 app 故障不影響其他 app」。
- 現在不開 HR app。帳戶不放進 HR。
- 現在不設計員工個人頁，它也不是登入落點。

**暫時不做（排在頁面成形之後）：**

- MCP 接口（C79）
- 生產部署（C79）
- 備份還原演練（C79，但上生產前必須做一次）
- 「對外存取」頁（C84，形態已定，等 `exposure` 落地才開工）
