---

## 0. 一句話

HR app 管「人由入職到離職」的整條鏈，包括計薪與 MPF；財務管付錢，不管算錢。

---

## 1. 邊界

**是：**
- 員工檔案：身份、合約、職級、薪酬歷史、銀行戶口、強積金帳戶
- 僱傭合約：簽署、續約、試用期、離職結算
- 計薪：底薪、津貼、佣金、加班、扣減、出糧單
- **MPF：僱員與僱主供款計算、供款記錄、受託人對帳**
- 假期：年假、病假、法定假期、無薪假、餘額累積
- 出勤：打卡、排班、補鐘（如需要）
- 招聘與入職：職位、面試、入職清單
- 離職：清單、最後薪酬、MPF 處理、離職面談

**不是：**
- 不做付款（HR 發起付款請求，財務執行）
- 不做總帳與入帳（HR 出彙總，財務入帳）
- 不做績效考核的完整系統（第一版只記錄評語，不做評分矩陣）
- 不做招聘廣告與履歷庫（第一版只記錄候選人與面試結果）

---

## 2. 為甚麼要獨立一個 app

三個理由：

1. **薪資是全公司最敏感的資料。** 放在財務 app 裡，「財務同事」就等於「看得到所有人薪金」。分開之後，權限可以窄得多：財務看到彙總，HR 與 Boss 看到明細。
2. **節奏不同。** 財務是每日看流水、每月結帳；HR 是每月一次出糧、平時處理假期與人事。兩者放一起，首頁要嘛擠，要嘛有一邊被忽略。
3. **計薪的知識密度高，而且會變。** MPF 上下限、平均工資計算、法定假期、連續性合約門檻，全部按當時法例與公司政策而定，且會修訂。這是一組需要版本化的規則，不是財務的一個子功能。

---

## 3. 香港法定的部分：不寫死，要版本化

這一節是 HR app 最容易出事的地方。

MPF 供款上下限、平均工資（713）的計算口徑、法定假期與年假累積、連續性合約的判定門檻——這些**都會隨法例修訂而變**。如果在程式碼裡寫死 `if 月薪 > 30000`，兩年後就要改程式，而且沒有人記得改過。

做法：

- 法定計算常數與公式放在 `Company Profile` 的 `statutory_rules`，帶 `effective_from`／`effective_to`
- 每次法例修訂 = 新增一個版本，不覆蓋舊版；歷史 payroll 永遠用當時的版本重算得到同樣結果
- 每張 Payslip 記錄用了哪個 `statutory_rules` 版本

> 具體數值不寫進本文件，因為它會過時。實作時逐項向官方來源核實，並記下來源與日期。

## 4. 概念模型

| 物件 | 一句定義 | Owner |
|---|---|---|
| **Employee** | 員工：身份、聯絡、銀行、MPF 帳戶、狀態 | ERPNext（主）＋ OS 前端 |
| **Contract** | 僱傭合約：類型、薪酬、試用期、起止 | **Company-OS**（ERP 沒有完整合約概念） |
| **Compensation Change** | 一次薪酬調整：原因、幅度、生效日 | **Company-OS** |
| **Payroll Run** | 一次出糧的執行記錄（含檢查與例外） | ERPNext（執行）＋ OS（編排與 Needs） |
| **Payslip** | 出糧單 | ERPNext（產生） |
| **Leave** | 一次請假申請與餘額變動 | ERPNext（主） |
| **Attendance** | 出勤記錄 | ERPNext／OS（視入口） |
| **MPF Record** | 一期供款：僱員、僱主、受託人、對帳狀態 | **Company-OS**（ERP 只記總額） |
| **Commission Input** | 計佣依據（由 Sales 經 MCP 提供） | Sales（擁有）→ HR（取用） |

`Contract`、`Compensation Change`、`MPF Record` 三個是 ERPNext 沒有的。ERP 有 Salary Slip 與 Salary Structure，但沒有「這份合約幾時到期、續不續」這種人事視角。

## 5. 畫面清單（異常優先）

**首頁：異常與待辦。** 無事時應該是空的。

| 區塊 | 顯示甚麼 |
|---|---|
| **出糧進度** | 本月 Payroll Run 卡在哪一步、有幾項例外未處理 |
| **未簽合約** | 已入職但合約未簽回 |
| **合約／試用期到期** | 60 日內，附「續／不續」的決定入口 |
| **假期異常** | 餘額負數、長期未放（合規風險）、集體同期請假 |
| **MPF 差異** | 本月供款 vs 上月，波動超過門檻 |
| **缺文件** | 身份證副本、學歷、前僱主證明、病假紙 |
| **等我判斷** | decision 型 Needs（薪酬調整確認、離職結算方案） |

其餘畫面：員工、計薪、假期、出勤、招聘、離職。

## 6. 一次出糧（Payroll Run）

```
① 收集輸入
      出勤、假期、加班、佣金（Sales 經 MCP）、本月的薪酬調整
      agent 檢查：有沒有人 missing 銀行戶口、合約過期、假期餘額負數

② 計薪
      ERPNext 按 Salary Structure 計；MPF 由 OS 的 statutory_rules 計算
      → 寫回 Salary Slip 的 deduction 項

③ 檢查（agent 自動，全部 pass 才繼續）
      本月 vs 上月總額差異、逐人差異超過門檻、新人／離職者是否正確
      異常 → Needs（decision 型，附差異原因推測）

④ 出糧單與付款
      產生 Payslip → 通知員工
      發付款請求去財務（HR 不直接付錢）

⑤ MPF 供款
      產生供款表 → 交受託人（External 或檔案上載）
      對帳：受託人回單 vs 我們計算 → 差異開 Needs

⑥ 記錄
      Payroll Run 關閉，留下完整執行記錄與所用的規則版本
```

同財務的 Closing Run 一樣：**由一個物件串起整條鏈**，任何一步有例外就開 Needs，能跑的繼續跑。

## 7. Needs 類型

**Decision 型**

| 類型 | 場景 |
|---|---|
| **薪酬調整確認** | agent 按晉升／市場資料建議，Boss 或 Manager 確認 |
| **出糧例外** | 某人金額變動異常、缺銀行戶口 |
| **離職結算方案** | 年假折算、代通知金、MPF 處理 |
| **續約決定** | 合約到期續不續、條款改不改 |

**Deliverable 型**

| 類型 | 場景 |
|---|---|
| **簽合約** | 新入職、續約（要實體或電子簽） |
| **交文件** | 身份證、學歷、前僱主證明、病假紙 |
| **MPF 表格** | 新員工登記表要簽名 |
| **見工** | 面試（要人到場，回報結果） |
| **離職面談** | 收集原因（這是策略校準的原料） |

## 8. Strategy Doc

| 策略文件 | 內容 | agent 用在哪 |
|---|---|---|
| **薪酬政策** | 職級與薪酬帶、調整節奏、加薪依據 | 薪酬調整建議 |
| **佣金規則** | 計佣公式、發放時點、離職時怎麼算 | 計薪、跟 Sales 對數 |
| **假期政策** | 各類假期的累積與使用規則（在法例之上的公司政策） | 假期審批建議、異常判斷 |
| **招聘標準** | 各職位的必要條件、面試問法 | 篩選與面試準備 |
| **離職處理** | 交接清單、通知期、最後薪酬做法 | 離職流程編排 |

「佣金規則」是這份 app 與 Sales 的交界：Sales 算成交，HR 算錢。兩邊用同一份規則文件，避免「Sales 說有、HR 說沒有」。

## 9. Automation

| Automation | 觸發 | 作用 |
|---|---|---|
| 出糧前檢查 | Payroll Run 開始時 | 逐項 pass／fail，異常開 Needs |
| MPF 計算 | Payroll Run 內 | 按法定規則版本計算，寫回 Salary Slip |
| 假期累積 | 每月 1 號 | 按政策累積、標示到期 |
| 合約到期提醒 | 每日 | 60／30 日內到期清單 |
| 試用期提醒 | 每日 | 到期前提醒做評估決定 |
| 佣金對帳 | 出糧前 | 向 Sales 取計佣依據，與 HR 計算比對 |
| 申報提醒 | 按事件 | 新入職／離職／年度報稅表的準備（由財務提交） |

全部是「計算、比對、提醒」。判斷一律變 Needs。

## 10. 與 ERPNext 的關係

| 資料 | 形態 | 方向 |
|---|---|---|
| Employee、Salary Structure、Salary Slip、Leave | 投影／鏡像 | ERP 為主，OS 只讀 |
| 計薪執行、假期批核、出勤 | Command | OS → Gateway → ERP |
| MPF 計算結果 | OS 計算 → 寫回 Salary Slip | 計算在 OS，記錄在 ERP |
| Contract、Compensation Change、MPF Record | OS 獨有 | 不進 ERP |
| 薪資總額、MPF 供款 | 彙總 → 財務（經 MCP） | OS 內部跨 app |

**為甚麼 MPF 計算在 OS 而不在 ERP：** ERPNext 的 Salary Structure 可以加 component，但香港 MPF 的上下限、自願性供款、離職時的處理，用 component 表達會變成一堆難以維護的公式。放在 OS 的一段 Python 裡，可以寫測試、可以版本化、可以重算歷史。這正是「Automation 平台級」那條原則的實際應用。

## 11. 與財務的分工（對照 `04` 第 13 節）

| 事情 | HR | 財務 |
|---|---|---|
| 計薪、MPF 計算、出糧單 | ✅ | — |
| 僱傭合約、入職離職、薪酬調整 | ✅ | — |
| 實際付款 | 發起請求 | ✅ 執行 |
| 薪資與 MPF 入帳 | 提供彙總 | ✅ 入帳 |
| 現金流的薪資線 | 提供 13 週預測 | ✅ 用於現金流 |
| 僱主報稅 | 提供資料 | ✅ 準備與提交 |

**權限的硬規則：財務只拿彙總，不拿逐人明細。** 除非 Boss 在 Portal 明確開啟。這一條同時是隱私保護，也避免財務被拉進人事判斷。

## 12. 工作型態、假期與計薪：三個維度相乘，不要一個 enum

「唔同種類嘅工作同計薪方法」是最容易寫成災難的地方。一定不要做 `employment_type` enum（全職／兼職／散工／外傭／實習…），因為它是三個獨立維度的乘積，寫成 enum 就會爆成幾十個分支，而且永遠少一個。

改成三個維度：

| 維度 | 值 | 屬於哪層 |
|---|---|---|
| **Work Pattern** | 具名組合，見下 | Tenant（可 Site 覆寫） |
| **Pay Components** | 底薪、時薪、日薪、津貼、佣金、加班、勤工、扣減、代通知金 | Tenant |
| **Holiday Calendar** | 該地點的假期與工作日 | **Site**（不同城市／不同假種） |

### Work Pattern 是甚麼

它不是一個類別，是一個**具名 bundle**：一組 Pay Components ＋ 一條計算公式 ＋ 一個 Calendar 規則。

| 例子 | 計法 |
|---|---|
| 全職月薪 | 底薪 ÷ 當月日數 × 實際工作日；假期照計 |
| 兼職時薪 | 時薪 × 實際工時；不足一小時按比例 |
| 日薪散工 | 日薪 × 出勤日；無假期累積 |
| 輪班制 | 底薪 ＋ 夜班／假日津貼；更表決定工時 |
| 計件 | 件數 × 單價；可能有底薪保底 |
| 佣金為主 | 低底薪 ＋ 佣金（計佣依據由 Sales 經 MCP 提供） |
| 住家外傭 | 月薪 ＋ 膳食津貼；合約年期固定 |
| 實習 | 津貼；無 MPF（視乎當地法例） |

**新工種不是新程式，是新 bundle。** 這是原則 6 的第二次應用（第一次是營運的計量維度）。加了第 9 種工種，不應該要改資料模型。

### 兩條要寫死

1. **假期日曆綁 Site，不綁 Tenant。** 同一間公司香港店與深圳店的公眾假期不同；即使同一個城市，也可能一批人跟銀行假、一批跟勞工假。
2. **出糧單與合約的語言綁 Tenant／法域，不綁 UI。** 法定文件可能要中英並列。員工看繁中介面，不代表他的合約可以只有繁中。

### 一個實際的設計含義

因為 Work Pattern 是 bundle，計薪的公式就不是「if 全職 else 兼職」，而是「讀這個 bundle 的 components，逐個計算再加總」。好處是：同一個人可以同時有兩種 pattern（例如底薪全職 ＋ 額外計件），不需要處理「混合型」這個特例——它自然支援。

## 13. 未決定

已答（v0.2）：工種與計薪不寫死，改為 Work Pattern × Pay Components × Calendar 三個維度；假期日曆綁 Site。

1. **現在怎樣計糧？** 你之前提到用 Google Form 收工時。這決定第一版是「先做資料入口」還是「先做計算」。
2. **佣金制有幾複雜？** 固定百分比，還是分段／團隊拆分／有門檻？這決定 `Commission Input` 的形狀與計佣公式。
3. **MPF 受託人是哪間？** 有沒有對帳單 API／檔案格式？
4. **第一版要支援幾個 Work Pattern？** 我建議先做「全職月薪 ＋ 兼職時薪 ＋ 佣金為主」三個，其餘留介面。
5. **出勤要不要打卡？** 如果現在沒有，第一版可能不做 Attendance，只做 Leave。
6. **績效考核**第一版做不做？我建議不做，只留評語欄位。
7. **員工看不看自己的 Payslip？** 給他們登入（多一批帳號與權限），還是繼續出 PDF 派發？

## 14. 下一步

HR app 的第一個決定不是畫面，是**範圍**。計薪是最容易做錯、又最痛的一塊，但它依賴三個未定的輸入（工時怎收、佣金怎算、MPF 受託人）。

所以我建議的次序是：**先做 Employee ＋ Contract ＋ Leave（人與合約，資料穩定）→ 再做 Payroll Run（依賴前兩者）→ 最後才做 MPF 對帳。**

先把人和合約做對，計薪才有基礎；反過來做的話，每次法例或政策改動都要回頭改資料模型。
