## 0. 一句話

營運 app 管「錢變成貨、貨變成交付」的整條實物鏈：買甚麼、幾時到、夠不夠用、怎麼送到客人手上。

---

## 1. 為甚麼與財務分開

一開始兩者合併的直覺是「同一批人做、錢的兩端」。但拆開看，兩者的資料性質與節奏完全不同：

| | 營運 | 財務 |
|---|---|---|
| 對象 | 實物（貨、料、批次、人手） | 數字（餘額、現金流、預算） |
| 節奏 | 每日、按事件 | 每日看、每月結 |
| 出錯的代價 | 缺貨、過期、送不到 | 現金斷、遲付款、帳目錯 |
| 主要資料來源 | ERPNext 庫存與採購 | ERPNext 總帳＋銀行 |
| 首頁要看的東西 | 缺料、過期、逾期未到 | 現金水位、逾期應收、月結進度 |

**強行合併的代價**是首頁要同時塞兩套完全不同的東西，最後兩邊都不好用。分開之後，兩個 app 各自有清楚的「第一眼」，而 Boss 的合併需求由 Portal 的總覽視圖滿足。

### 三者的交界

```
Sales：成交之前（人、報價、談判）
   ↓ 成交（Sales Order）
營運：成交之後的實物（採購、庫存、交付）
   ↓ 交付完成
財務：錢的流動（開票、收款、付款、預測）
```

## 2. 計量維度：全支援，按公司啟用（不是三選一）

三條業務線的「庫存」不是同一件事：

| 業務 | 庫存是甚麼 | 核心問題 |
|---|---|---|
| **SPA／美容** | **消耗品**：每次療程用掉幾多 | 夠不夠用、幾時要補、每次療程成本幾多 |
| **家具** | **件**：一張單等一張梳化 | 邊張單等邊件貨、幾時送得到、安裝要幾個人 |
| **食品** | **批次**：同一款貨有不同到期日 | 邊批快過期、冷鏈有沒有斷、每日出幾多 |

**但這三種不是「全部」，只是這間公司剛好用到的三種。** Company-OS 會裝在不同公司，所以不可以把計量方式寫成三個枚舉——寫死就等於第 4 種要改 schema、改計算、改 UI，那這套 OS 只賣得一間公司。

做法：**計量是一組可疊加的維度，不是三選一。**

| 維度 | 意思 | 誰會用 |
|---|---|---|
| `consumption` | 按用量扣減（每次療程用幾多） | 美容、診所、餐飲 |
| `piece` ＋ `reserved` | 逐件，可預留給某張單 | 家具、設備、零售 |
| `batch` ＋ `expiry` | 批次與到期日，先進先出 | 食品、化妝品、藥品 |
| `serial` | 逐件序號，可追溯個別機件 | 電子、保養維修 |
| `weight` ／ `volume` | 散裝計重／計容積 | 食材、化工 |
| `service` | 不佔庫存，只是勞務 | 安裝、療程本身 |
| `kit` | 組合件：一組料當一件用 | 套裝、BOM 式配套 |

**一個 Item 可以同時帶多個維度。** 例：一批面膜 = `batch` ＋ `expiry` ＋ `piece`；一個療程 = `service`，另扣減數個 `consumption` 的料；一件訂製梳化 = `piece` ＋ `reserved`，另扣 `consumption` 的布。

可用量、扣減方法、預警邏輯，全部按**維度組合**計算，不是按一個 `tracking_mode`。

**哪個維度真的啟用，由 Company Profile 決定，可以按品牌不同。** 美容品牌開 `consumption`；家具品牌開 `piece`＋`reserved`；食品品牌開 `batch`＋`expiry`。同一個 app、同一份 schema、同一個 instance。

這條是「一個部門一個 app」的第一次真實壓力測試。如果為了統一而把三種壓成一種，三條業務都不合用；如果做三個 app，又違反「一個部門一個 app」。正確答案是**一個 app、一組可配置的計量維度**。

**代價要講清楚：** 維度化之後，每個維度要各自寫扣減與可用量規則，測試組合會變多。這是通用化的成本，但比「每間公司一套分支」便宜得多。

## 3. 邊界

**是：**
- 採購全流程：需求 → 詢價 → PO → 收貨 → 驗收 → 退貨
- 供應商檔案與交期表現
- 庫存：可用量、預留、在途、批次、到期、調撥、盤點、損耗
- **耗用記錄**（美容業的核心，也是成本核算的來源）
- 交付履行：送貨排程、安裝、配送
- 缺貨與過期的預測

**不是：**
- 不做生產排程（MRP）。第一版不做，三條業務都用不到。
- 不做物流追蹤。只記錄「已交付／未交付」，不追車。
- 不做成本會計的分錄。成本由 ERP 算，營運只提供耗用與收貨數據。
- 不做付款。付款是財務 app 的事，營運只發起「付款申請」。

## 4. 概念模型

| 物件 | 一句定義 | Owner |
|---|---|---|
| **Supplier** | 供應商：聯絡、交期、價格歷史、表現評分 | Company-OS |
| **Item** | 物料／商品；帶一組 `tracking_dims`（可多個）與 `safety_stock` | ERPNext（主）＋ OS 鏡像 |
| **Purchase Order** | 採購單 | ERPNext |
| **Receipt** | 收貨與驗收記錄（含短交、破損） | ERPNext（單）＋ OS（驗收細節、照片） |
| **Stock** | 可用量、預留、在途、批次、到期 | ERPNext（投影） |
| **Consumption** | 一次耗用（療程用了幾多支精華） | **Company-OS**（ERP 沒有這個概念） |
| **Fulfilment** | 一次交付任務：送貨、安裝、配送 | Company-OS |
| **Stock Count** | 盤點：計劃、實盤、差異 | Company-OS（差異過帳去 ERP） |

`Consumption` 是這個 app 最獨特、也最值錢的物件。ERP 只知「庫存少了」，不知「為哪個客人、哪個療程少的」。有了這條，才可以算「每個療程的材料成本」，也才可以預測「再過幾多日要補貨」。

## 5. 畫面清單（異常優先）

**首頁：異常與待辦。** 無事時應該是空的。

| 區塊 | 顯示甚麼 |
|---|---|
| **斷料風險** | 低於安全庫存的料，按「幾日內會用完」排序 |
| **即將過期** | 食品批次，30 日內到期，按價值排序 |
| **卡住的單** | 已成交但缺料、無法交付的 Sales Order |
| **逾期未到** | PO 過了交期仍未收貨 |
| **待驗收** | 貨已到、未驗收（超過 24 小時標紅） |
| **今日／本週交付** | 送貨與安裝排程 |
| **待盤點** | 到期未盤的倉／店 |

其餘五個畫面：採購、庫存、供應商、交付、盤點。

**兩個 UX 原則（與 Sales 一致）：**
1. 每一行都要能一鍵變成 agent 指令（「幫我補呢隻貨」、「幫我問供應商交期」）。
2. 數字要標新鮮度（庫存是投影，可能 30 秒前的）。

## 6. 一個採購循環

```
① 需求出現（三種來源：安全庫存線、某張單要用、人手提出）
      agent 巡查 → 判斷「真的要買」→ 開一張採購 Project
      判斷依據：「採購策略」策略文件（幾時補、補幾多、用邊個供應商）

② 詢價／比價
      agent 拉價格歷史與供應商交期 → 建議 2–3 個選擇
      缺報價 → Needs（要人打電話問）

③ PO
      Staff 確認 → Command 經 Gateway 建 PO（ERPNext）

④ 收貨
      貨到 → Needs（要人點貨、拍照）
      Staff 或店長上載收貨記錄與照片 → agent 標籤入庫
      短交／破損 → 自動開一張「追討」Needs

⑤ 驗收與入庫
      合格 → Command 過帳（ERP Stock Entry）
      不合格 → 退貨流程

⑥ 付款申請
      交去財務 app：付款排程由財務決定，營運不碰錢
```

## 7. Needs 類型

| 類型 | 場景 |
|---|---|
| **收貨點貨** | 貨到，要人實際點件數、拍照、簽收 |
| **盤點** | 月結／季結實盤 |
| **樣品確認** | 新供應商、新物料，要人摸過睇過 |
| **見供應商** | 談價、談交期、談品質問題 |
| **送貨人手** | 大件貨要兩個人、要特定時段 |
| **破損拍照** | 收貨發現問題，要證據 |

Needs Email 規格沿用 Sales 那套：短、三樣背景、一條 project page 連結、不要用附件回覆。

## 8. Strategy Doc

| 策略文件 | 內容 | agent 用在哪 |
|---|---|---|
| **採購策略** | 幾時補、補幾多（安全庫存／經濟批量）、用邊個供應商優先 | 巡查時決定買不買、買幾多 |
| **庫存策略** | 各類貨的周轉目標、容許損耗率、盤點頻率 | 判斷異常 |
| **交付策略** | 送貨時段、區域劃分、安裝人手要求 | 排程建議 |
| **品質標準** | 收貨驗收標準（外觀、規格、證書） | 驗收判斷、退貨建議 |

## 9. Automation

| Automation | 觸發 | 作用 |
|---|---|---|
| 安全庫存巡檢 | 每日 07:00 | 找出低於線的料，按「幾日用完」排序 |
| 耗用自動扣減 | 療程完成事件 | 按療程類型扣減消耗品，寫 Consumption |
| 保鮮期預警 | 每日 06:00 | 30 日內到期批次清單 |
| PO 逾期提醒 | 每日 08:00 | 過交期未收貨，開 Needs |
| 交付完成回寫 | 交付簽收後 | 回寫 Sales 的 SO 狀態、開票觸發 |
| 供應商交期評分 | 每週 | 按實際到貨 vs 承諾日期計分 |

全部是「同步」與「提醒」，沒有一條是「判斷」。

## 10. 與 ERPNext 的關係

| 資料 | 形態 | 方向 |
|---|---|---|
| Item、Stock、PO、Receipt | 投影（即時查）／部分鏡像 | ERP 為主，OS 只讀 |
| 收貨過帳、PO 建立、盤點差異 | Command | OS → Gateway → ERP |
| Consumption、Fulfilment、驗收細節 | OS 獨有 | 不進 ERP |

**Gateway 的共用問題（誠實講）：** 之前定「ERP 連接只給真正需要的 app」。現在 Sales、營運、財務三個都需要，所以 **Gateway 會變成平台服務，但每個 app 要註冊自己可以用哪些 doctype**。Marketing 仍然不接——這一點沒變。

## 11. 未決定

已答（v0.2）：計量不寫死三種，改為可疊加維度、全部支援、按公司啟用。

1. **耗用數據從哪來？** 療程記錄在 Sales app、預約系統、還是手工輸入？這決定 Consumption 是自動還是半自動。
2. **多倉／多店面**：一個品牌幾間店？庫存要分店看還是合併看？
3. **第一版開哪幾個維度？** 雖然全部支援，但實作次序要排——我建議 `consumption`＋`piece`＋`batch`（因為你三條業務都要），`serial`／`weight`／`kit` 留介面但不做。
4. **交付排程**：要不要路線優化？還是只做「邊日、邊個人、邊張單」？
5. **誰做收貨**：店長、倉務、還是前線？這影響 Needs 的指派邏輯。
6. **盤點差異幾時過帳**：即時，還是月結一次？

## 12. 下一步

這個 app 最大的未知不是設計，是**數據來源**：耗用、盤點、收貨這三件事，現在是靠人記、靠紙、還是靠某個系統？如果是靠人記，第一版的真正工作是把數據入口做好，而不是把畫面做靚。
