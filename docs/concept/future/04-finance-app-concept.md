# 財務 App 構思總覽

版本 v0.3 ｜ 2026-11-10 ｜ 狀態：討論稿（已對齊 `01` v0.7）  
上位文件：`01-company-os-concept.md`。姊妹文件：`02-sales-app-concept.md`、`03-operations-app-concept.md`、`05-hr-app-concept.md`。老闆版摘要見 `00-master-plan.md`。

> **v0.3 只是對齊，不改設計**：① 多幣種已定案，本文件所有金額一律 `{amount, currency}`，Tenant 有 `base_currency`，匯率版本化；② 「會計剩下 10% 變 Needs」與 `01` 第 7 節的 `decision` 型鐵律一致（agent 必須先做一次並附建議）；③ 監管保留由框架強制，財務憑證不可被 UI 直接刪（`01` 第 4 節）；④ 第一版不做 Finance（`01` 第 14 節），但**銀行流水走哪條路**（API／匯出檔／PDF）要在動工前答，因為它決定這個 app 的自動化上限。

> v0.2 的四處改動（全部由用户定）：
> 1. 「會計全自動」剩下的 10% **不再假設要人坐低做，而是一律變成 Needs**。
> 2. 銀行流水 **三條路全支援**（API／CSV／PDF），可疊加，不是三選一。
> 3. 財務角色 **先接受外判**，因此新增 `External` 角色（極窄權限）。
> 4. 薪資與 MPF **移到 HR app**，財務經 MCP 取錢相關部分。

---

## 0. 一句話

財務 app 把「錢的流動」變成可預測、可控；會計能自動的全自動，**不能自動的全部變成 Needs 派出去**，人只做判斷。

---

## 1. 它與 Sales、營運的分工

同一份應收，兩種用途，不要混淆：

| | Sales | 財務 |
|---|---|---|
| 應收帳 | **看**：决定要不要再放帳 | **管**：追收、帳齡、壞帳風險 |
| 發票 | 開（服務客人） | 核對、入帳、對稅 |
| 應付 | 不碰 | 付款排程、現金折扣、供應商對帳 |
| 現金流 | 不碰 | 預測、缺口預警 |

營運產生應付（收貨 → 付款申請），Sales 產生應收（成交 → 開票），財務在中間管兩端。

---

## 2. 「會計全自動」：把那 10% 變成 Needs

先講結論：**目標不是 100% 無人，而是「人不需要主動想起會計」**。凡是需要判斷的環節，agent 不停下來等，而是**帶着答案開一張 Needs**。

| 環節 | 誰做 | 形態 |
|---|---|---|
| 交易分錄（開票、收款、收貨、付款） | ERPNext | 全自動，單據一產生就過帳 |
| 折舊、匯兌重估、規則明確的攤銷 | worker | 全自動，按月跑 |
| 管理報表、試算平衡 | worker | 全自動 |
| **應計／攤銷（金額與期間要判斷）** | agent 準備 → **Needs** | 附合約、歷史、建議分錄，人按一個掣 |
| **銀行對帳的例外** | agent 配對 → **Needs** | 九成自動配對，餘下每條流水一張，附建議配對 |
| **月結的例外判斷** | agent 判斷 → **Needs** | Closing Run 卡住就開，不靜靜跳過 |
| **稅務申報** | 外判會計師 → **Needs** | 法律責任在人，agent 只做準備與核對 |
| 外部審計 | 會計師 | 不在系統內 |

**關鍵轉變：agent 不是「停下來等」，而是「帶着答案來問」。** 每張這類 Needs 必須附三樣：

1. 已做好的工作（建議分錄／建議配對／計算過程）
2. 依據（哪份合約、哪條政策、哪張單）
3. 一個「同意就按」的動作

人做的是**複核**，不是輸入。這是「會計由輸入員變成審核員」的實際意思。

### 為甚麼這比 approval gate 好

- **不是流程閘，是工作清單。** 沒有東西要判斷時，Needs 根本不存在，Closing Run 直接跑完。
- **不阻塞。** 一張 Needs 未答，其餘 98% 照跑，月結不會因為等一個人而停住。
- **有痕跡。** 每張 Needs 記錄了 agent 當時提議甚麼、人改成甚麼。年底檢討「為甚麼這筆是這樣分」時有得查，而 approval gate 只會留下「approved by」。

## 3. 銀行流水：三條路全支援

沒有流水就沒有自動對帳。但**不是揀一條路，是三條都支援、可疊加**。

| 路 | 取得方式 | 延遲 | 成本 | 角色 |
|---|---|---|---|---|
| **A** | 銀行 API（企業網銀／Open API） | 即時～每日 | 要申請、可能有月費 | 主力 |
| **B** | 每日／每週匯出 CSV／Excel | 一日 | 一兩個手動動作 | 覆蓋大部分銀行 |
| **C** | 月結單 PDF 抽取 | 一個月 | 最差、要人核 | 底部保障 |

**做法：一個 `Bank Feed` 抽象、三個 adapter、可並存。** 同一間銀行可以 A 為主 C 為備；同一間公司可以甲銀行用 A、乙銀行只有 C。每個戶口記自己的 `feed_level`，UI 明示「這個戶口只有 PDF 級，對帳可信度較低」——不假裝齊全。

**三路並存必須處理重複。** 同一筆款可能由 API 與 PDF 各進一次。做法：流水指紋（日期＋金額＋參考號＋對手方）跨來源去重；去重不了就開一張 Needs 問人，而不是靜靜合併。**寧願問，不要猜。**

## 4. 邊界

**是：**
- 應收：帳齡、催收、壞帳風險、信用額監控
- 應付：付款排程、現金折扣判斷、供應商對帳單
- 費用報銷：提交、政策檢查、批核、付款
- 現金流預測：13 週滾動，含情境
- 預算：設定、執行率、偏差
- **月結編排**：把散落的自動化步驟串成一個 Closing Run
- 銀行流水取得與對帳（三路）
- 異常監控：毛利率突變、費用超標、現金低於閾值

**不是：**
- 不做法定財務報表（ERPNext 出，會計師核）
- 不做稅務申報（只做準備，申報由人簽）
- 不取代會計師或審計
- 不做應收融資、匯率對沖
- 不改總帳結構（科目表在 ERP）
- **不算薪、不算 MPF**（在 HR app）

## 5. 概念模型

| 物件 | 一句定義 | Owner |
|---|---|---|
| **Invoice** | 發票（應收／應付） | ERPNext（投影） |
| **Payment** | 一次收款或付款 | ERPNext（Command 寫入） |
| **Bank Feed** | 一個戶口的流水來源連線（API／CSV／PDF），帶 `feed_level` 與最後同步時間 | Company-OS |
| **Bank Line** | 一條流水，待配對 | Company-OS（從 feed 取得，跨來源去重） |
| **Reconciliation** | 配對結果：哪條流水對哪張單 | Company-OS（結果回寫 ERP） |
| **Expense Claim** | 報銷單 | Company-OS ＋ ERP（付款後） |
| **Cashflow Forecast** | 13 週現金預測 | **Company-OS 獨有** |
| **Budget** | 預算：按品牌／部門／科目 | **Company-OS 獨有** |
| **Closing Run** | 一次月結的執行記錄 | **Company-OS 獨有** |

`Cashflow Forecast`、`Budget`、`Closing Run` 三個是 ERP 沒有的——這也是財務 app 存在的理由。ERP 記已發生，這三個管未發生。

`Bank Feed` 是 v0.2 新增的：把「流水從哪來、到不到、準不準」變成一個看得見的物件，而不是一行寫死的設定。

## 6. 畫面清單（異常優先）

**首頁：異常與待辦。** 無事時應該是空的。

| 區塊 | 顯示甚麼 |
|---|---|
| **現金水位** | 各品牌、合併；今日 vs 未來 13 週最低點 |
| **資金缺口** | 哪一週會負數，缺口幾多 |
| **逾期應收 Top 10** | 按金額與逾期天數排序，附「建議動作」 |
| **大額待付** | 本週要付的，附「延後代價」（現金折扣／關係） |
| **月結進度** | Closing Run 卡在哪一步、卡在等誰 |
| **等我判斷** | decision 型 Needs 的清單（對帳例外、應計、稅務） |
| **流水斷線** | 哪個 Bank Feed 超過預期時間沒新流水 |
| **報銷待批** | 超過 N 日未批的標紅 |
| **異常** | 毛利率突變、費用超預算、重複付款嫌疑 |

其餘畫面：應收、應付、報銷、預算、月結、對帳、銀行來源。

**兩個 UX 原則：**
1. 每個數字都要能點入看「由邊幾張單組成」——財務不接受黑盒。
2. 每個異常都要有一個「叫 agent 處理」的入口。

## 7. 現金流預測：三條線、薪資線、固定支出

這是**第一條真正需要跨 app 的流程**，也是你早前那個決定的第一個受益者：

```
應收（ERP）          ← 已開票未收，按帳期與歷史收款速度推算
應付（ERP）          ← 已收貨未付，按帳期
Pipeline（Sales）    ← 未成交但有機會，按階段成功率加權      ← 經 MCP 問 Sales
薪資與 MPF（HR）      ← 未來 13 週已知薪資、假期、增減人手      ← 經 MCP 問 HR
固定支出（OS）        ← 租金、訂閱、保險
─────────────────────────────
13 週 rolling 現金曲線
```

兩條跨 app 線各有意義：Pipeline 是 ERP 永遠不知的「可能有單」；薪資是 ERP 只有已發生、不知「下個月請人」。財務 agent 兩邊都用唯讀摘要，不抄表。

**每週一自動重算**，保留歷史版本——這樣才可以事後檢討「為甚麼上個月估錯」。

## 8. Needs 類型

財務的 Needs 分兩大類，這也是全 OS 的兩型（見 `01` 第 7 節）：

**Decision 型（要判斷／授權／簽名，不需交檔案）**

| 類型 | 場景 |
|---|---|
| **分錄判斷** | 應計、攤銷、調整分錄，agent 建議好等人按 |
| **對帳例外** | 配對不上、金額差、重複嫌疑 |
| **付款授權** | 超過門檻 |
| **稅務確認** | 申報前核對 |
| **簽名** | 支票、匯款指示、銀行文件 |

**Deliverable 型（要交東西）**

| 類型 | 場景 |
|---|---|
| **收據補交** | 報銷缺單據 |
| **銀行文件** | 月結單、開戶文件、信用狀 |
| **見會計師／銀行** | 審計、融資（要人到場，回報結果） |

Decision 型的密度會隨自動化提高而下降，但它永遠不會歸零——因為稅務責任與簽名權永遠在人。

## 9. Strategy Doc

| 策略文件 | 內容 | agent 用在哪 |
|---|---|---|
| **收款策略** | 幾時催、用甚麼語氣、幾時停供、壞帳門檻 | 催收動作、風險標記 |
| **付款策略** | 付款優先次序、帳期運用、現金折扣取捨 | 付款排程建議 |
| **預算規則** | 誰可以超、超幾多要批、滾動預算做法 | 偏差判斷 |
| **費用政策** | 報銷上限、可報與不可報、審批門檻 | 報銷自動檢查 |
| **月結日曆** | 每月幾號做甚麼、誰負責、依賴誰 | Closing Run 編排 |
| **會計判斷原則** | 這間公司對應計、收入確認、攤銷的既定做法 | **產生建議分錄時的依據**（v0.2 新增，配合 Needs 化） |

最後一份是新的、也是關鍵的：既然判斷要外派，agent 就必須**先按公司既定做法做一次**，人只在偏離時才出聲。沒有這份文件，每張 Needs 都會變成「你自己填」。

## 10. Automation（這個 app 最多）

| Automation | 觸發 | 作用 |
|---|---|---|
| 流水抓取 | 每日 08:00 | 按各 Bank Feed 的 adapter 取數（API／CSV／PDF） |
| 跨來源去重 | 流水進來後 | 指紋比對，可疑的開 Needs |
| 自動對帳 | 去重後 | 配對發票與付款，只留例外 |
| 催收草稿 | 逾期第 7／14／30 日 | 按收款策略起草郵件，Staff 按發送 |
| 付款排程 | 每週一 | 按付款策略排出本週付款建議 |
| 月結 Closing Run | 每月 1 號 | 跑第 11 節那條鏈 |
| 匯率更新 | 每日 | 更新未結外幣單的估值 |
| AR／AP 快照 | 每日 | 供應收應付與現金流用 |
| 薪資資料同步 | HR 出糧後 | 取彙總入帳、更新現金流薪資線 |
| 預算偏差計算 | 每週 | 標出超支科目 |
| 重複付款偵測 | 付款前 | 同金額同供應商短期內兩次 → 攔住問人 |

全部是「同步、計算、防錯」，沒有一條是「代替人做判斷」。判斷一律變 Needs。

## 11. 月結的實際樣子（Closing Run）

```
Day 1  凍結交易（鎖定當月，之後的單入下月）
   ↓
Day 1  銀行對帳（自動配對 → 例外開 Needs，不等人）
   ↓
Day 2  應計與攤銷（agent 按會計判斷原則產生分錄建議 → Needs）
   ↓
Day 2  折舊、匯兌重估（全自動）
   ↓
Day 2  薪資入帳（向 HR 取彙總 → 自動分錄）
   ↓
Day 3  試算平衡檢查（不平就停，不准過）
   ↓
Day 3  出管理報表（損益、分部、現金流）
   ↓
Day 4  交外判會計師／老闆看 → 有問題回頭改
   ↓
       Closing Run 關閉，留下完整執行記錄
```

**兩個設計重點：**

- **整條鏈由一個 `Closing Run` 物件串起**，否則月結會變成一堆散落小腳本，沒人知道跑到哪一步。
- **開 Needs 不等於停住。** 能跑的繼續跑，Closing Run 只在「試算不平」這種硬條件才真停。這是與傳統月結 checklist 最大的分別。

## 12. 與 ERPNext 的關係

| 資料 | 形態 | 方向 |
|---|---|---|
| GL、Invoice、Payment、科目表 | 投影／鏡像 | ERP 為主，OS 只讀 |
| 付款、收款登記、調整分錄 | Command | OS → Gateway → ERP |
| 對帳結果 | OS 計算 → 回寫 ERP | 配對完成後在 ERP 標記 |
| Cashflow、Budget、Closing Run、Bank Feed | OS 獨有 | 不進 ERP |

**外判會計師不需要一個 Company-OS 帳號。** 他拿到的是 `External` 角色（見 `01` 第 5 節）：一個只有 **Needs inbox** 的極窄介面——看得到指派給他的 decision 型 Needs、相關單據與附件，可以按確認或留言。他仍然可以進 ERPNext 看原始分錄，那是他的專業工具，我們不取代。

這條很重要：如果把外判會計師當成 Staff 拉進 OS，就要給他部門 app 權限、要教他用整套系統， adoption 一定失敗。他只應該見到「今日有三筆要你判斷」。

## 13. 與 HR 的分工（已定 2026-11-10）

**薪資與 MPF 在 HR app，不在財務。** 但財務要讀得到錢的部分。

| 事情 | 誰做 |
|---|---|
| 計薪、MPF 計算、假期扣減、出糧單 | **HR** |
| 僱傭合約、入職離職、薪酬調整 | **HR** |
| 實際付款（轉帳、支票） | **財務**（HR 只發起付款請求） |
| 薪資總額、MPF 供款入帳 | **財務**（經 MCP 取彙總） |
| 現金流的薪資線 | **財務**（經 MCP 取未來 13 週預測） |
| 僱主報稅（IR56B） | **財務** 準備，HR 提供資料 |

原則跟 Sales／Marketing 一樣：**HR 擁有薪資資料，財務不抄一份表，而是經 MCP 取。** 財務拿到的是彙總與時序，不是逐人明細——除非 Boss 在 Portal 開權限。這一條同時保護了薪資隱私：一般財務人員看得到「本月薪資總額 38 萬」，看不到張三幾多錢。

## 14. 未決定

已答（v0.2）：銀行流水三路全支援；財務角色先接受外判；薪資與 MPF 歸 HR。

仍然未定：

1. **外判會計師用不用我們的 Needs inbox？** 還是繼續用電郵／WhatsApp 收問題？（用 inbox 是他要學一樣新東西，但不用就沒有痕跡）
2. **多品牌帳目**：分開幾套帳，還是一套帳多維度分析？你已定「分開但可合併總覽」，要落實在資料模型上。
3. **報銷政策**：現在有沒有人手流程？上限怎定？
4. **預算**：現在有沒有做預算？如果沒有，第一版可能從「記錄實際」開始，而不是「比較預算」。
5. **稅務**：香港利得稅、還是涉及多地？這影響報表結構。
6. **會計判斷原則誰寫？** 這份策略文件是財務 app 新依賴，但它需要專業知識——Boss 寫，還是外判會計師寫、Boss 確認？

## 15. 下一步

財務 app 的設計難度已經從「數據來源」轉到**「Needs 的顆粒度」**：

- 太粗：一張 Needs 包五筆對帳例外，人要看半小時，等於沒有自動化。
- 太細：每筆流水一張，人會被淹沒。

合理的做法是**按「同一個判斷」聚合**——同一供應商、同一原因、同一處理方式的例外合成一張，附「全部同意」按鈕。這一點要等有真實流水才知道怎麼切，所以第一版可以先做細，觀察兩星期再合併。
