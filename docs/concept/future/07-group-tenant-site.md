# 組織層級：Group / Tenant / Site

版本 v0.2 ｜ 2026-11-10 ｜ 狀態：討論稿（已對齊 `01` v0.7）  
上位文件：`01-company-os-concept.md`。姊妹文件：`06-app-library.md`。老闆版摘要見 `00-master-plan.md`。

> **v0.2 對齊**：① 組織目標＝**形狀 B（一公司多店）**，但第一版是 **1 Tenant : 1 Site**，多店留 P1（`01` 第 13 節）；② **多幣種已定案**：每個 Tenant 一個 `base_currency`，跨幣種只做換算顯示，不做跨幣種合併入帳；③ 定位改為「自家基建、不公開賣」，所以「加盟總部最強賣點」那一句是**假設**，不是現行商業模式。

> 這份回答三件事：**多據點怎麼部署、Boss 怎麼看全部、多語言與多法域怎麼放。**
> 還有一個副產品：加盟與「每個地點是一間獨立公司」在技術上是同一件事。

---

## 0. 一句話

**Site 自治、Tenant 擁有、Group 只看。** 事件永遠向上流，master 永遠在最低那一層。

---

## 1. 三層，不是兩層

原本寫「一間公司一個 instance」。這句話對單店成立，對多據點就不夠。改成三層：

| 層 | 是甚麼 | 對應實體 | 一台機？ |
|---|---|---|---|
| **Site** | 一個地點的運作單位 | 一間店、一個倉、一個診所 | ✅ 一個 instance |
| **Tenant** | 一個法律實體（一間公司） | 有自己帳目、稅號、合約 | 可以 1 機，也可以 N 機 |
| **Group** | 老闆的持有結構 | 持股、家族、加盟總部 | ❌ 不是機器，是一個視圖 |

三種常見形狀：

```
A. 單店          Site = Tenant = Group（一個 instance 搞定）

B. 同一公司多店   Tenant 1 ── Site 1, Site 2, Site 3
                  （主站 + 衛星站，master 在主站）

C. 每個地點一間公司 Tenant 1 ─ Site 1
                  Tenant 2 ─ Site 2       ── Group
                  Tenant 3 ─ Site 3
```

**你說的「each location one machine one company」就是形狀 C。** 而加盟是形狀 C 再加 royalty 與品牌合規。**兩者用同一套層級，不需要兩套設計。** 這就是為甚麼加盟幾乎免費。

---

## 2. 每一層擁有甚麼

這是整份文件最重要的一張表。寫錯這張，日後所有同步都會錯。

| 資料 | 主人 | 為甚麼在這一層 |
|---|---|---|
| 客戶檔案、產品與價目、科目表、員工 | **Tenant** | 法律實體擁有，跨店共用 |
| 庫存（在手）、預約、排班、門市現金 | **Site** | 物理上在那一間店 |
| 帳目、稅、合約、薪酬結構 | **Tenant** | 法律責任在法人 |
| Project、Needs、Create | **Site**（產出留在出身 app） | 工作在那間店發生 |
| 集團持股、跨 tenant 比較、加盟 royalty | **Group** | 只有這一層看得到全部 |

**一條硬規則：建立與修改只在 master 所在層。** 衛星站可以讀客戶（唯讀副本），但不能改；要改就提交一個 intent 回主站。這跟 Sales 對 ERP 的「投影／鏡像／命令」三態是同一個模式，只是換了層級。

---

## 3. 為甚麼一店一機（而不是全部上雲）

三個理由，第三個最重要：

1. **斷網仍能做生意。** 收銀、預約、開單不應該因為網絡斷了而停。
2. **資料本地。** 相片、影片、render 產出全部在本地 MinIO，不靠雲端頻寬。
3. **合規。** 有些地區的客戶資料不能出境。如果將來有內地或其他地區的店，本地存放是唯一安全做法。

代價是：多機就要同步，同步就有衝突。所以下面兩節就是處理這件事。

---

## 4. Hub：只存投影與事件，永不存 master

Boss 要跨店看數，就需要一個匯集點。叫 Hub。

**Hub 的職責只有三件：**

1. **投影**：各 site 推上來的摘要（今日營業額、庫存水位、未完成 Needs 數、異常清單）。**不是完整資料。**
2. **事件**：append-only 的事件流，用來做事後追溯與跨店比較。
3. **指令下發**：Boss 或集團層發出的指示，回到具體 site 執行。

**Hub 絕不存 master。** 客戶、產品、帳目永遠在 tenant／site。這一條跟「成品不回流中央」是同一個理由：**一旦中央有一份可寫的副本，就會出現兩個真相。**

Hub 放哪裡：一部小雲 VM，或者 Boss 自己機器上的一個容器。它不需要高效能，因為它只收摘要。

---

## 5. Hub 死掉會怎樣（必須事前答）

答案要寫死：**各 site 照常運作。**

- 收銀、預約、開單、render 全部不受影響
- 只是看不到跨店視圖、不能跨店調撥、不能跨店查客
- Hub 恢復後，site 會補推積壓的事件（事件帶時間戳，順序由 site 保證）

這叫 **Site 自治，Hub 不被日常運作依賴**。如果做不到這一點，Hub 就是單點故障，多據點設計就失敗。

**同理：主站（master site）死了，衛星站仍能運作多久？** 這是必須定的數字。做法是衛星站持有唯讀主資料副本，可以撐到「需要新增客戶或改價」為止。這個時間窗口要定，我建議至少 7 天。

---

## 6. 跨店流程：三個真實場景

| 場景 | 做法 | 為甚麼不簡單做 |
|---|---|---|
| **跨店查客**（客人在 A 店買過，去 B 店） | B 店的 agent 經 Hub 查，或直接問 A 店 | 需要 identity 知道「這個客屬於哪個 tenant」 |
| **跨店庫存調撥** | A 店開出 transfer → B 店確認收貨 → 兩邊各自扣加 | **不能單邊寫**。單邊寫就會出現「A 扣了 B 沒加」 |
| **跨店員工調更** | HR（tenant 級）擁有僱傭；排班（site 級）各自 | 一個人可以有多店的排班，但合約只有一份 |

第二條是重點：**任何跨 site 的交易都是兩個獨立交易 + 一個協調記錄**，不是一個跨庫 transaction。分散式 transaction 在斷網環境做不到，也不應該做。

## 7. 加盟：形狀 C 加兩樣東西

| 加盟額外要的 | 屬於哪層 |
|---|---|
| 加盟商名冊、合約、期限 | Group |
| **Royalty 計算**（按營業額或進貨額） | Group（要讀各 tenant 的數） |
| 品牌合規審核（用色、字體、話術、店面） | Group（Marketing 出一份 checklist，加盟商交相） |
| 選址與開店支援 | Group |
| 培訓 | Group |

**Royalty 是最難的一塊**，因為它要信任：總部憑甚麼信加盟商報的營業額？如果加盟商用我們的 OS，數字是系統出的，不是他報的——**這其實是 Company-OS 對加盟總部最強的賣點**：不是軟件，是可驗證的分潤基礎。

這也是為甚麼我說「即使第一版不做加盟，也要預留 tenant 維度」。

## 8. 多語言：三個層，不要混

這是最容易做錯的地方，因為「語言」在三個地方出現，各有各的主人。

| 層 | 屬於誰 | 例子 | 錯了會怎樣 |
|---|---|---|---|
| **UI 語言** | 每個使用者 | 香港同事看繁中，內地同事看簡中，外籍同事看英文 | 如果寫在公司設定，外籍同事要整個介面跟著變 |
| **內容語言** | 每個 Asset／Doc | 品牌語氣指引是繁中版；IG 文案是英文版 | 如果跟 UI，同一個客會收到兩種語言的文案 |
| **法定文件語言** | 每個 Tenant／法域 | 出糧單、僱傭合約、發票可能要中英並列 | 如果只做一種，法律上不成立 |

**三條推論：**

1. **Agent 回覆用 staff 的 UI 語言**（存在 Preference Doc 裡）。
2. **Marketing 產出的語言由 channel 與策略決定，不由 UI 決定。** 做英文 IG 就出英文，即使做的人看繁中介面。這是最多人搞錯的一條。
3. **Strategy Doc 帶 `locale`。** 同一個品牌可能有中英兩份語氣指引，agent 按產出語言揀對的那份——這正好是既有「策略多點分佈、agent 揀啱份」機制的自然延伸，不需要新機制。

## 9. 多法域：假期、工作型態、薪酬

### 假期

`HolidayCalendar` 綁 **Site**，不綁 Tenant。理由：香港與內地同一間公司的假期不同；即使同一城市，不同店可能跟不同假（例如跟銀行假 vs 勞工假）。

### 法定規則

`statutory_rules` 綁 **Tenant**，但允許 Site override。因為通常是同一法域，但跨法域（香港 + 深圳）就要覆寫。這跟 `05` 的版本化設計一致：帶 `effective_from`／`effective_to`，永不覆蓋。

### 工作型態與計薪

這是 `05` 要補的一節。**不要做「僱傭類型 enum」**，那會爆炸成幾十種組合。改成三個獨立維度相乘：

| 維度 | 值 |
|---|---|
| **Work Pattern**（具名組合） | 全職月薪、兼職時薪、日薪散工、輪班制、計件、佣金為主、住家外傭、實習 |
| **Pay Components**（清單） | 底薪、時薪、津貼、佣金、加班、勤工、扣減、代通知金 |
| **Calendar** | 該 site 的假期與工作日 |

一個「Work Pattern」其實就是「一組 Pay Components + 一條計算公式 + 一個 Calendar」的具名 bundle。新工種不是新程式，是新 bundle。**這是原則 6 的第二次應用**（第一次是計量維度）。

---

## 10. 刻意不做

| 不做 | 為甚麼 |
|---|---|
| Hub 存完整 master | 會出現兩個真相 |
| 跨 site 即時雙向同步 | 衝突解不掉 |
| 跨 site 分散式 transaction | 斷網環境做不到，也不該做 |
| 為每個 site 一套獨立 schema | 版本會分裂，升級地獄 |
| 統一「集團客戶庫」 | 每個 tenant 的客是自己的，合併是法律與隱私問題 |

## 11. 未決定

**已答（v0.2）**：① Hub 是選配，單店不需要（第一版 1 Tenant : 1 Site，所以 Hub 暫不啟動）；② **多幣種**已定案——每 Tenant 一個 `base_currency`，匯率版本化，跨幣種只做換算顯示；③ Boss 的帳號：**一個身份、多個 tenant 授權**（不開多個帳號，否則審計會出現「兩個人」）。

仍然未定：

1. **主站放哪裡？** 總店？一部雲 VM？Boss 的機器？（決定衛星站斷線窗口）
2. **衛星站可以離線多久？** 我建議 7 天（唯讀主資料副本的容忍上限）。
3. **加盟 royalty 的基礎**：營業額、進貨額、還是兩者取高？（先用哪個試點）
4. **UI 語言第一版做幾個？** 我建議繁中 + 英文，簡中留介面但不翻譯。
5. **跨幣種合併報表要不要做？** 我建議第一版只做「各自幣種、可切換顯示」，合併報表（需要集團匯率政策）留到真的多 tenant 時才做。
