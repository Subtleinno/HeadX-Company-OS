## 1. 先講清楚 HxDesign 現在真正是什麼

這決定了一切，所以先講事實（不是文件寫的，是程式碼證明的）。

### 它真的做好了（我們**不應該**重複做）

| 能力 | 證據 |
|---|---|
| 真實認證：scrypt 密碼、HttpOnly session（30 日）、登入節流、首啟鎖 | `core/auth.mjs`、`routes/auth.mjs` |
| MCP agent 之門：`POST /mcp`，Bearer `hxm_…`，token 綁 workspace、DB 只存 SHA-256 | `routes/mcp.mjs:517`、migration `0004` |
| **恰好 6 個動詞工具，全部真的做事**：`browse`／`read`／`write`／`find`／`render`／`help` | `mcp.mjs:22-29`，每個標 `x-hx-status: live` |
| 三層 ACL（workspace / folder / project），四級 `none < view < edit < manage` | `0006`、`packages/policy` 的 `resolveAccess` |
| `audit_log` 用 DB trigger 強制 append-only；`GET /audit` 可讀（super_admin） | `0001`、`server.mjs:271` |
| 成品儲存 `create_deliverable` + HTTP Range／206 串流 | `0009`、`create.mjs` |
| `HX-###` 全安裝唯一編號（編號即地址） | `create_project_ref_seq` |
| Studio 已變成服務（Docker），HYPERFRAMES 已寫成文件 | `docker/studio`、`docs/product/HYPERFRAMES.md` |
| CI 綠：migrate → test → build，pgvector 映像 | `.github/workflows/ci.yml` |

### 它刻意沒做，而且**是設計決定**

| 缺什麼 | 原因 |
|---|---|
| **沒有任何批准機制** | `DECISIONS.md` **D08**：「批准移除，用設計師與客戶自訂的標籤取代；判斷前移到輸入端的 Keep。」GitHub code search 對 `approval` 回 0 結果 |
| 沒有 `contracts/` | 2026-10-16 `9514fe6` 一次過刪掉 12 個 schema 檔 |

**這兩個「刻意不做」是整份設計最重要的輸入。**

它們說明：
1. 團隊不想在創作工具裡被批准流程卡住 → **批准應該在創作之外**
2. HxDesign 不想當平台 → **它只想當一個 app**

**而這正好就是 Company OS 存在的理由。**

### 它仍然缺的（Company OS 應該做）

- 跨 app 的政策閘道、風險分級、金額上限（全 repo 零命中）
- 有終態的驗收狀態機（`delivered` 這個值沒有任何 code path 寫它）
- 事件的**推送**（`GET /audit` 只有 LIMIT 100、super_admin、無 filter）
- token TTL 與輪替（`mcp_token` 沒有 expiry）
- 雜湊鏈審計（HxDesign 用 trigger 保證 append-only，**不是 hash chain**）
- Needs 工單（HxDesign 的 `gaps` 是「專案還缺什麼 context」，不是「要人做一張單」）

## 2. 形狀：三層，職責不重疊

你選了「形狀 C：公司入門套件」。這不等於「所有 app 合併成一個大系統」——那會變成怪獸。我的解讀是：

```
┌──────────────────────────────────────────────────────────┐
│  第一層：COMPANY OS（只服務老闆）                          │
│                                                          │
│  批准收件匣 · Needs 派工 · 風險分級 · 金額上限            │
│  熔斷開關 · 雜湊鏈審計 · 全景 Dashboard                   │
│                                                          │
│  ＊ 不儲存業務文件。只儲存「決定、授權、日誌」。            │
│  ＊ 只有一個使用者：老闆。                                  │
└──────────────────────┬───────────────────────────────────┘
                       │ 所有 agent 的寫入都經這裡
┌──────────────────────▼───────────────────────────────────┐
│  第二層：AGENT RUNTIME（DSH + Super Agent）                │
│                                                          │
│  讀 issue → 開工單 → 在獨立目錄工作 → 開 PR                │
│  撞牆時開 Needs                                           │
└──────────────────────┬───────────────────────────────────┘
                       │ MCP（唯一合法通道）
┌──────────────────────▼───────────────────────────────────┐
│  第三層：APPS（各有自己的團隊、自己的資料）                 │
│                                                          │
│  HxDesign（設計）· ERP（營運）· ERPNext（會計）           │
│  WordPress（網站）                                        │
│                                                          │
│  ＊ 每個 app 自己管自己的團隊、自己的權限、自己的介面。      │
│  ＊ Company OS 只透過 MCP 與它們對話，不進它們的資料庫。     │
└──────────────────────────────────────────────────────────┘
```

### 為什麼這樣切，而不是合併

| 你的要求 | 這個切法怎樣滿足 |
|---|---|
| 「Company-OS 只服務老闆」 | 第一層只有一個使用者。團隊永遠不需要登入 Company OS。 |
| 「不同團隊用不同工具」 | 第三層每個 app 自己一套認證與權限。設計師用 HxDesign，會計用 ERPNext，互不相干。 |
| 「未來開新品牌／新公司要快」 | 複製入門套件＝複製「三層的設定」，不是複製三套程式碼。 |
| 「Super Agent 可以自己繼續做」 | 第二層所有寫入都經第一層，所以它做什麼、被擋在哪裡，全部可見、可審、可成長。 |

## 3. 「公司入門套件」到底包含什麼

**創辦人已定案：一間公司＝一台電腦。** 那台電腦裝上入門套件，就有一個完整的公司管理系統；一間公司之下可以有多個品牌。

### 這個決定有多重要（它令整件事簡單了 5 倍）

| 如果用「一個網站服務多間公司」 | 如果用「一間公司一台電腦」 |
|---|---|
| 要做多租戶：tenant id、資料隔離、跨租戶越權測試 | **不需要**。資料隔離由機器邊界天然保證 |
| 一個 bug 可能洩漏另一間公司的資料 | 物理上不可能 |
| 要處理「哪間公司登入」、全域帳號 | 一台機只有一間公司，老闆只有一個帳號 |
| 授權、計費、配額 | 不需要 |
| 備份要分租戶 | 整台機備份即可 |

**你用硬件邊界取代了軟件邊界。這是這個設計裡最聰明的一個決定。**

### 入門套件的內容

```
company-starter/
├── company.config.json    ← 公司名、品牌清單、角色、風險表、金額上限
├── apps.manifest.json     ← 這間公司用哪些 app、各自的 MCP 端點與 scope
├── secrets/               ← 每個品牌獨立金鑰（永不進 git）
├── docker-compose.yml     ← 一鍵起：Company OS + 各 app + 資料庫
└── README.md              ← 五步啟動指南
```

開一間新公司：

```
新電腦 → 裝 Docker → 複製這五樣 → 改公司名與品牌 → 填金鑰 → docker compose up
```

**半天之內，一間新公司就有自己的管理系統。**

### 品牌隔離在哪一層

因為一台機只有一間公司，品牌隔離變成**機內隔離**，而不是跨租戶隔離：

| 層 | 隔離什麼 | 機制 |
|---|---|---|
| 金鑰 | 每個品牌一把獨立金鑰 | `secrets/brand-a.env`、`secrets/brand-b.env` |
| 資料庫 | 每個品牌自己的 schema 或 workspace id | 沿用 HxDesign 的三層 ACL 做法 |
| 審計 | 每一筆都帶 `brandId` | Company OS 已實作 |
| 網頁介面 | 進入品牌模式要明確標示 | 設計系統已規定 |

### 為什麼不現在建多租戶

你之前選過「先內部用，保留產品化路徑」。而「一台機一間公司」令這個選擇變得毫無代價——**你根本不需要現在決定要不要多租戶**，因為硬件邊界已經解決了隔離問題。

日後真的要變成 SaaS，才需要把那台機變成一個容器、加上 tenant 概念。到時要改的只有「讀設定」那一層。

## 4. 最關鍵的設計：系統如何自己成長

這是「super agent 可以自己繼續做，而且越做越好」的機制。它不是靠更強的模型，而是靠**一個閉環**。

```
① Agent 想做一件事
        ↓
② Company OS 查動作登錄表（config/actions.json）
   ├─ L0／L1 → 放行，記審計
   ├─ L2／L3 → 進批准收件匣，等老闆
   └─ L4 → 直接擋
        ↓
③ 老闆在收件匣按批准／退回（附結構化理由代碼）
        ↓
④ 決定寫入雜湊鏈審計
        ↓
⑤ 每週，Agent 讀自己的審計：
   「這個 L2 動作我批了 12 次，老闆從未改過」
        ↓
⑥ Agent 開一個 PR：把該動作由 L2 降為 L1，附上 12 次紀錄作證據
        ↓
⑦ 老闆合併＝政策改變。系統自己變得更快。
```

### 這個閉環的三個關鍵設計

| 設計 | 為什麼 |
|---|---|
| **政策是資料，住在 git** | `config/actions.json` 是版本化的。改政策＝改檔案＝有 diff、有 PR、可回滾。不是藏在某個 UI 的設定裡。 |
| **降級必須有證據** | Agent 不能憑感覺說「這個安全」，要引用具體的批准紀錄。防它自我放寬。 |
| **升級要人合併** | 政策改動永遠經 PR。**MCP 不提供批准工具**（ADR-016 已定），所以 agent 連「自己批准自己」的路都封死。 |

### 這才是「自己成長」的真實含義

不是「agent 變聰明」，而是：
> **老闆的每一次批准／退回，都會變成系統的規則。**
> 老闆做得越久，要批的東西越少。

而這正是你「每日 2 小時」的唯一可能路徑。

## 5. HxDesign 要保留、改造，還是重寫？

**創辦人已定案：不改、不刪 HxDesign。它是「參考實現」，可以抄，不可以依附。**

### 這個決定的意思

| | 意思 |
|---|---|
| **不改不刪** | HxDesign 繼續按它自己的節奏發展（40% → 100%）。我們不動它一行。 |
| **參考實現** | 它是一份已經走過彎路的答案卷。入門套件要抄它的**做法**，不是抄它的**程式**。 |
| **可以抄的東西**（做法，不是檔案） | ① `POST /mcp` + Bearer token 的 agent 門設計<br>② **6 個動詞**的工具切法（`browse`／`read`／`write`／`find`／`render`／`help`）—— 比 31 個名好得多<br>③ 三層 ACL（workspace / folder / project）＋ 四級 `none < view < edit < manage`<br>④ append-only 審計用 DB trigger 強制，而不是靠程式自律<br>⑤ 成品用 `Range`／206 串流，不用 base64<br>⑥ `HX-###` 編號即地址<br>⑦ 首啟鎖（`pg_advisory_xact_lock` 防止兩個人同時建立第一個管理員）<br>⑧ CI：migrate → test → build，用與正式相同的映像 |
| **不可以抄的** | 它的資料庫、它的資料、它的 workspace 概念。入門套件要有自己的資料模型。 |
| **不可以做的** | 叫入門套件「依賴」HxDesign。一旦依賴，HxDesign 就永遠不能改，等於把它變成瓶頸。 |

### 為什麼這個決定是對的

1. **它證明了 6 動詞的切法是可行的** —— 有 smoke 測試走到 Range 206。這是省下幾個月試錯的禮物。
2. **它的 D08（刻意移除批准）教了我們最重要的一課**：批准不應該塞進創作工具。入門套件的設計應用也要守這條。
3. **不依附，才不會互相拖住。** 它繼續做它的設計 OS，入門套件做它的公司基座，兩者可以各自演化。

### 抄的時候要記住

> **抄「為什麼這樣做」，不要只抄「這樣做」。**

例如：它的審計用 trigger 而不用應用層程式，原因是「應用層會忘記」。抄它的時候要連這個理由一齊抄，否則改一點點就會破功。

## 6. 兩套審計，不要合併

| | HxDesign `audit_log` | Company OS 審計 |
|---|---|---|
| 記什麼 | 創作系統內發生什麼事（誰加了成品、誰改了 ACL） | **誰授權了什麼**（哪個人批准了哪個動作，基於哪個政策版本） |
| 防篡改 | DB trigger 禁止 UPDATE／DELETE | sha256 雜湊鏈，任何改動令整條鏈斷 |
| 對外 | `GET /audit`（super_admin、LIMIT 100） | MCP `company_os_audit_verify` |
| 誰看 | 該 workspace 的管理者 | **老闆** |

**不合併的理由**：合併就會出現「兩個真相」。而且它們的用途完全不同——一個是操作日誌，一個是授權鏈。

## 11. 我要你決定的下一件事

上面第 10 節的八步，第 2 至 7 步是「引擎」，第 8 步是「第一個 app」。

**問題：先做引擎（第 2–7 步），還是先做第一個 app（第 8 步）？**

| 選項 | 好處 | 風險 |
|---|---|---|
| **先做引擎** | 地基穩，之後每個 app 都接得上；符合你「future proof」的要求 | 有一段時間看不到具體成果 |
| **先做第一個 app** | 很快有一個能用的設計工具 | 之後要回頭改造它去接閘道，等於重做 |
| **兩者交錯** | 引擎做一個能力，就用它接一個 app 的功能 | 需要紀律，但最快見到成果 |

**我的建議：兩者交錯，但引擎永遠領先半步。** 具體做法是：引擎每完成一個能力，就用真實 app 的功能去驗證它，而不是用假的測試。
