# Company-OS 全盤計劃（老闆版）

版本 v1.0 ｜ 2026-11-10 ｜ 讀者：你（不需要技術背景）  
這份是導覽與判斷依據。技術細節在 `01`–`10`，你不需要讀，除非想追某一個決定。

---

## 0. 一句話

**一套你自己擁有、裝在自己機器上的系統，把公司的策略、記憶、產出集中在同一處；AI agent 在裡面做大部分工作，人只補 agent 做不到的部分，你只落策略、看全貌。**

不是買一套 ERP，也不是租一個 SaaS。是**你開公司用的基建**。

---

## 1. 它要解決的四個現況問題

| 現況 | 後果 |
|---|---|
| 公司知識散在 WhatsApp、Excel、各人腦裡 | 每次由零開始；人一走就帶走 |
| 同一件事每次做法不同 | 品質靠運氣，不靠系統 |
| 想用 AI，但 AI 沒有公司上下文 | 產出「很漂亮但不像我公司」 |
| 想請 AI 做事，它做不到就靜靜地給你一個半成品 | 你不知道缺什麼，也不知道缺的那塊誰來補 |

第四條是這套設計的原點，也是它與市面上大部分「AI 工具」最大的分別。

---

## 2. 三個核心想法（所有設計由此推出）

**一、agent 是主要執行者，人是判斷者。**  
不是「有 AI 輔助的 ERP」，是「有畫面的 agent 平台」。所以系統的第一等公民是給 agent 用的接口，畫面是給人看結果與補位。

**二、做不到，就開一張工單（叫 Needs）。**  
不是錯誤訊息，不是靜靜降級，是一張有原因、有期限、指名叫誰做的卡。人做完上載，agent 吸收、標籤、入庫、回填。這條閉環是全套系統最值錢的地方。

**三、策略你寫，agent 只負責揀與跟。**  
策略不是 AI 生成，是你手動加入的多份文件（品牌語氣、渠道規範、步驟順序）。agent 接到任務時自己揀對的那幾份，然後全程跟住做。你不寫，它就沒有方向。

---

## 3. 系統長怎樣：三層

```
你 → Boss Portal（全公司總覽：專案、Needs、排程）
        ↑ 只讀，不插手
部門 app（Marketing、Sales、Operations、Finance、HR…）
        ↑ 每個 app 擁有自己的資料與產出
平台殼（切換 app、身份權限、註冊表、事件日誌）
        ↑
Postgres（狀態與紀錄）＋ MinIO（檔案與成品）
```

**一個關鍵邊界：成品留在出身的 app，不回流中央。** Marketing 做的圖與片留在 Marketing 的 Create；Portal 只顯示「有幾件、什麼狀態」，不存放成品。  
理由很實際：中央一旦有一份可寫的副本，就會出現兩個真相，之後沒人敢改。

---

## 4. 日常怎樣運作（一個真實例子）

同事對 agent 說：「做一個介紹品牌的 IG Carousel。」

| 步 | agent 做什麼 | 你／同事做什麼 |
|---|---|---|
| 1 | 判斷屬 Marketing，開一個專案 | — |
| 2 | 揀策略文件（品牌層＋渠道層＋步驟層） | — |
| 3 | 從四個庫取材：品牌素材、知識文件、相片影片、版面範本 | — |
| 4 | 組出一份完整設計稿（可預覽、可重現） | — |
| 5A | **資料齊** → 直接出成品，存入 Create | 同事看成品；不滿意就說「再改」 |
| 5B | **資料不齊** → 開 Needs、專案存成半成品 | 同事收到需求 → 製作 → 上載 |
| 6 | 上載後自動標籤、描述、入庫、回填專案 → 出成品 | — |

**5B 不是失敗，是正常路徑。** 而且每次補的素材都會成為下次可重用的資產——這是系統會越用越順的原因。

## 5. 員工會見到什麼

- **一個 Needs 收件箱**：今日有幾張卡、每張要做什麼、為什麼要、何時要、去哪個專案頁交。沒有附件往來，沒有群組追問。
- **自己部門 app 的工作台**：列表、詳情、成品。
- **沒有**：一堆審批關卡、填不完的表單、為了流程而存在的欄位。

對外發送（Email、訊息）永遠由人按最後一下，agent 只準備到「可以發」為止。

---

## 6. 部門 app 有幾多

不是三五個，是一個**圖書館**，每間公司按業務開啟：

| 層 | App | 什麼公司要 |
|---|---|---|
| 幾乎每間都要 | Sales、Finance、HR、Marketing | 有客、有錢、有人、有對外形象 |
| 視業務開啟 | Operations（採購庫存）、Support（客服）、Booking（預約套票）、Commerce（電商）、Product Studio（設計模具）、Logistics（貨運） | 做實物、做售後、做預約、做網店、做研發、做車隊 |
| 特殊模式 | Franchise（加盟） | 特許經營 |

**圖書館沒有的，系統幫你生出來。** 這叫 **App Forge**：你講一句「我要一個加盟管理」，系統問你幾個問題（單店還是多店、收什麼貨幣、要不要保留憑證），產出一頁規格，然後編譯成一個可以註冊上線的 app。

它的作用是：**我們不必預先寫好所有 app，也不必為了新業務改動整個系統。** 加一個部門，是加一份規格，不是改地基。

## 7. 機器、資料、錢

**部署：一個地點一部機。** 店裡斷網仍然可以收銀、開單、出圖；資料在本地，不靠雲端頻寬；有些地區的客戶資料不能出境，本地存放是唯一安全做法。

每一部機跑五個服務（資料庫、檔案庫、平台接口、前端、背景工作），用 Docker 起，`docker compose up` 就是一台。

**固定成本只有幾類**（實際金額隨你選的硬件與用量）：

| 項目 | 說明 |
|---|---|
| 一部 mini PC ＋ SSD | 每個地點一部；相片影片體積大，SSD 要夠 |
| 備份位置 | 外接硬碟或雲端物件儲存，必須在地點以外 |
| AI 模型用量 | 按 token 計；這是變動成本，也是最容易被低估的一項 |
| 網域與憑證 | 小額 |
| （可選）雲端小主機 | 多店時才需要，用來匯集各店摘要 |

**市場上不需要買 ERP 授權**：ERPNext 是開源、自己跑。但它只由 agent 操作，人不登入。

## 8. 怎樣確保不會亂：三色規則

你一個人擁有所有源碼，而大部分改動由 agent 做。所以「什麼可以改」不能寫在文件裡靠它聽話，而是**用機器擋**。

| 區 | 內容 | 規則 |
|---|---|---|
| **紅** | 地基：資料格式、註冊契約、權限、備份腳本、測試與 CI | agent 技術上改不到；要改必須你親手，而且會留下紀錄 |
| **黃** | 新增物件、改流程、加接口 | 可以改，但要寫一頁「為什麼這樣決定、否決了什麼」 |
| **綠** | 畫面、文案、查詢、報表、公司配置 | 自由 |

三條配套，缺一不可：

1. **agent 用自己的帳號**，不是用你的。它可以交改動，但永遠不能自己批准、自己合併。
2. **用「改動前」的測試去驗「改動後」的程式**——這條叫 base-pinned proof gate。它直接消滅最常見的走捷徑方式：改測試讓自己過關。
3. **憲章短、配方具體。** 叫 agent 讀的規則檔只寫三樣（怎麼跑、禁區、決策索引），一百行以內；真正有用的是「要做這件事就這樣做」的六份配方（加物件、加接口、加工單類型、加公司變體、改資料格式、加 app）。

## 9. 「無 bug」的真相，與三個可以承諾的東西

**沒有人做得到無 bug。** 微軟出貨級軟件約每千行 0.5 個缺陷；業界頂尖團隊的「改動導致故障率」也有 8–16%。一個兩萬行的部門 app，期望值是約十個缺陷在生產。

所以我不會承諾無 bug，我建議承諾三句可以驗的：

1. **任何一次改動，15 分鐘內可以回到上一個正常狀態。**
2. **資料最多掉一小時；四小時內回復；而且每季真的試一次還原**（不是看備份成功日誌）。
3. **一個 app 壞，不影響其他 app 讀資料。**

**還有一件事要老實講：你現在擔心的方向，和真實風險排序是倒轉的。** 企業系統出事的主因依次是：權限與設定改錯、備份存在但還原不到、資料格式改動失敗、硬件與第三方、最後才是程式邏輯錯誤。你（和大部分工程師）的時間幾乎全押在最後一項。所以流程要把前四項放前面。

## 10. 做的次序（不要跳）

| 階段 | 做什麼 | 為什麼這個次序 |
|---|---|---|
| **0** | 地基與圍欄：程式庫、CI、bot 帳號、**設計 tokens 與五個版面原型**、備份與還原演練、三色規則 | 圍欄要在屋之前。先寫功能再想邊界，等於先建屋再畫地界 |
| **1** | 平台殼 ＋ **Boss Portal v0** ＋ Marketing Design | 第一個 app 驗證整條閉環（策略→取材→成品→Needs→回填） |
| **2** | Sales（**只切一條線**：客戶＋報價＋授權 Needs＋報價 PDF） | 第二個 app 才令註冊契約真的被測；而且是第一個「人主場」的 app |
| **3** | 抽出 App Kit，然後才做 **Forge** | Kit 要由兩個真實 app 反推，不是憑空猜。生成的第一個目標是細而真實的 app |
| **4** | Operations、Finance、HR、其餘 | 概念已寫好，按痛點排 |

**第一階段不要做多。** 一個 app 做到底，比五個 app 做一半有價值。

（階段 0–2 合起來就是「第一版」。**Boss Portal 不是 Forge 生成的 app**——它是殼，讀的是註冊契約；用生成物去做總覽，等於平台依賴生成物。詳見 `11-delivery-plan.md` 第 1 節。）

|---|---|---|
| 1 | 第一版要不要同時做一個 Forge 生成的 app？ | **不要，順延到階段 3**。Kit 要由兩個真實 app 反推；先做 Forge 等於三個未驗證的東西互相依賴（`11` §1.3） |
| 2 | 程式庫用 GitHub 還是自架 Gitea？ | **GitHub 私有庫 ＋ bot 帳號**（已定） |
| 3 | 第一版要不要建「多公司」結構（但只裝一間）？ | **要，只建結構**。日後加公司是填資料，不是重構 |
| 4 | 策略文件先給我一份真實樣本？ | **要**。這決定 agent 怎麼揀，是唯一「沒樣本就寫不下去」的東西 |
| 5 | `Needs` 要不要改名？ | 可改可不改。市面上已有三個產品用同名，但對內使用不構成問題 |
| 6 | 第一版成品只做影片與圖片（PDF 留後）？ | 修改：Marketing 只做圖片與影片；**Sales 的報價 PDF 要做**，它是 derived 管線的第一個真實使用者 |
| 7 | 銀行流水用哪條路（API／匯出檔／PDF）？ | **先做匯出檔**，最穩定；API 要申請，PDF 抽取最易錯 |

另有十幾條較細的未決事項，分散在 `01`–`10` 各文件尾，不影響開工。

## 12. 三個風險，老實講

**一、範圍會失控。** 這套東西可以無限長。唯一剎車是「六條不變量」——框架只認物件擁有權、三層組織、任務自主度、工單兩型、註冊四 shape、事件格式。其餘一律不進框架。這條紀律比任何功能都重要。

**二、你會變成唯一的瓶頸。** 研究數據很清楚：AI 讓你寫得快、審得慢，而**審查產能才是上限**。所以設計上要讓每個改動只看三樣（有沒有碰紅區、加了幾個新東西、驗證跑到哪一級），其餘不看。

**三、生成太多、沒人收。** 業界觀察：一個用戶半年試十五到二十個 app，約一半被棄置——它們沒壞，只是沒有主人。所以每個 app 都要有 owner，90 天沒活動就自動開一張卡問「繼續、歸檔、還是退役」。
