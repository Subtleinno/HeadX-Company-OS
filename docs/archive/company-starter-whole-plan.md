# 公司入門套件：整體計劃（用一個實驗證明它會work）

日期：2026-11-03
依據：本機已跑通的實驗（`proof/`，下文附實測輸出）
定位：HxDesign 只是其中「設計與行銷」那一塊；這份是全部

---

## 一、我先做了一個實驗，證明「策略可以被機器檢查」

計劃書最大的問題是「聽起來很好」。所以我先不做計劃，先做一個能跑的東西。

### 實驗設計

| 項目 | 內容 |
|---|---|
| 目標 | 證明「一條策略條款」可以由程式自動判斷合不合格，不需要人看 |
| 素材 | 一支真實渲染的 1080×1920 Reels 影片（HyperFrames，12 秒，360 幀） |
| 對照組 | v1：字幕壓在底部 40px（平台介面遮擋區）；v2：字幕移到 360px |
| 檢查器 | `proof/lint.mjs` —— 把 `catalog` 裡 `mandatory` 的條款逐條執行 |
| 規則來源 | `proof/catalog/video.json`（政策即資料，門檻值也寫在裡面，不寫死在程式） |

### 實測結果（不是預期，是實際輸出）

**v1（違規版）**

```
策略：video.caption-spatial-story  (字幕空間敘事)
規格：1080x1920 · 12.00s · 360 幀

  [PASS] r1 caption-track — 字幕需全程存在，且可在播放器中關閉。
  [FAIL] r2 safe-zone — 字幕不得進入平台介面遮擋區。
         上帶 max=0.00 (241 幀)；下帶 max=14.90 (241 幀)；門檻 5
  [SKIP] r3 hook-2s — 前 2 秒需出現整支片的主張。
         指引類條款，需人判斷
  [PASS] r4 dimension — 尺寸與長度需符合子渠道格式。
  [PASS] r5 duration — 長度不得超過平台上限。

結論：fail   (pass 3 / fail 1 / skip 1)      ← 離開碼 1
```

**v2（合規版）**

```
  [PASS] r2 safe-zone — 字幕不得進入平台介面遮擋區。
         上帶 max=0.00 (241 幀)；下帶 max=0.00 (241 幀)；門檻 5

結論：pass   (pass 4 / fail 0 / skip 1)      ← 離開碼 0
```

### 這個實驗真正證明了三件事

| # | 證明了什麼 | 為什麼重要 |
|---|---|---|
| 1 | **策略條款可以機械化** | 「字幕不得進入遮擋區」變成 `check: safe-zone`，程式會抓，人不用記得 |
| 2 | **錯誤會被擋在交付之前** | 離開碼 1。將來的 CI、MCP 工具、匯出流程都可以據此拒絕 |
| 3 | **指引類條款誠實跳過** | `hook-2s` 標明「需人判斷」，不假裝通過。**不作假是這個系統可信的前提** |

### 它**沒有**證明的事（要老實講）

| 未證明 | 影響 |
|---|---|
| 只用一支影片、一個品牌、一條策略 | 換品牌、換語言、換平台時，門檻值要重新校準 |
| `safe-zone` 用的是「邊緣能量」啟發式 | 背景本身很花的時候會誤判。需要按品牌調 `maxEdgeEnergy` |
| `caption-track` 檢查的是原始碼，不是畫面 | 如果有人把字幕燒死在圖裡，這個檢查會漏 |
| 「做得好不好看」完全沒驗證 | 它只驗「合不合規」，不驗「美不美」。美仍要人與 `oil-ui` 判斷 |

**我把界線畫清楚，因為一個假裝萬能的檢查器比沒有檢查器更危險。**

## 二、由此得出一個統一形狀：每個部門都是四件套

實驗裡真正有價值的不是「影片檢查」，而是**那個結構**。我把同一個結構套到公司的每一個部分：

```
① 目錄（catalog）      政策即資料，版本化在 git
        ↓
② 專案（project）      一次具體的工作，帶知識與缺口
        ↓
③ 條款（mandatory）    可機器驗證的規則 + 指引類條款
        ↓
④ 缺口（Need）         做不到的交給人，記成缺口不硬湊
```

**設計與行銷用它，銷售也用它，財務也用它。這就是「一個 base 可以用一輩子」的意思。**

| 部門 | ① 目錄 | ② 專案 | ③ 條款 | ④ 缺口 |
|---|---|---|---|---|
| 設計／行銷 | 策略目錄、渠道格式 | 一次創作（網站／影片／排版／3D） | 安全區、長度、字幕軌 | 缺實拍、缺旁白 → Need |
| 銷售 | 銷售階段、報價規則 | 一單交易 | 折扣上限、必要欄位 | 缺客戶資料 → Need |
| 營運／ERP | 流程與庫存規則 | 一張訂單 | 數量、交期、批次 | 缺貨 → Need |
| 財務 | 入帳規則、稅務 | 一張發票／一筆對帳 | 金額、科目、期間 | 缺單據 → Need |
| 人事 | 職位、入職清單 | 一個招聘／一次入職 | 必備文件、權限 | 缺合約 → Need |
| 客服 | 回覆政策、SLA | 一張工單 | 回覆時限、敏感詞 | 缺資料 → Need |
| 網站／內容 | 發佈政策 | 一次發佈 | 連結、alt、結構 | 缺素材 → Need |

**你不需要為每個部門設計新架構。你只需要為每個部門填一次這四格。**

## 三、整體形狀：一台機、一間公司、一個 repo

```
一間公司 = 一台電腦
        └── 一個 repo（Company-OS）
              ├── engine/          Company OS：政策閘道、批准收件匣、審計
              ├── parts/
              │     ├── design/    ← HxDesign 演進成的「設計與行銷」部分
              │     ├── sales/
              │     ├── ops/
              │     ├── finance/
              │     ├── people/
              │     └── support/
              ├── skill/           一個 skill + references/（漸進揭露路由）
              └── config/          company.config.json、apps.manifest.json
```

### 為什麼一個 repo

| 理由 | 說明 |
|---|---|
| 使用者裝一次 | 你講的：install one repo once |
| 條款檢查器共用 | `lint.mjs` 一份，所有部門用 |
| 批准收件匣只有一個 | 你只在一個地方批 |
| 版本一致 | 不會出現「設計那邊更新了、財務那邊還在舊版」 |

### 為什麼仍然分 `parts/`

因為**每個部門由不同的人（或 agent）維護**，混在一起就沒法獨立演進。分目錄、不分 repo。

## 四、建造次序（為什麼設計先做）

| 次序 | 部分 | 理由 |
|---|---|---|
| **1** | **設計與行銷**（HxDesign） | 已有 40% 的實作與一份 41KB 的真實策略目錄；而且它是**唯一一個已經證明「條款可機器檢查」的部分** |
| 2 | 品牌與知識（橫向） | 設計依賴它，其他部門也會用 |
| 3 | Company OS 的批准與 Needs 落地 | 你每天 2 小時的那個介面 |
| 4 | 銷售 | 有收入才有其他 |
| 5 | 營運／財務 | 有單才有帳 |
| 6 | 人事／客服 | 有規模才需要 |

**先做設計不是因為它最重要，是因為它能最快證明整套模式成立。** 現在它已經證明了。

## 五、每個部門如何驗收：同一把尺

任何一個部分做完，必須能回答這五條：

| # | 問題 | 不合格的樣子 |
|---|---|---|
| 1 | 它的目錄是不是純資料，改它＝改檔案有 diff？ | 規則藏在程式碼或某個 UI 設定裡 |
| 2 | 它有沒有至少一條 `kind: lint` 的條款，而且真的會 fail？ | 只有 `guidance`，等於沒有檢查 |
| 3 | 檢查器的門檻是不是寫在目錄裡？ | 門檻硬編碼，換品牌要改程式 |
| 4 | 它有沒有 `gaps`，而且匯出時會記成待補？ | 缺東西時硬湊一個 |
| 5 | 它做不到的事有沒有變成 Need 給人？ | agent 假裝做到 |

**這五條就是「whole company」的品質閘。** 任何部分過不了，就不算完成。

## 六、你每天 2 小時的那個循環

```
① 你打開批准收件匣（L2／L3 請求）
        ↓ 批准 / 退回（附理由代碼）
② 你開 Needs 給同事（或 AI 已開好，你確認）
        ↓
③ 同事交付 → 你驗收（或 AI 先用 lint 預檢）
        ↓
④ 每週：agent 讀自己的審計，提議把某些 L2 降為 L1
        ↓ 你合併 PR ＝ 政策改變
⑤ 下一週要批的東西變少
```

**這是「越做越少」的唯一機制。** 它靠的不是更強的模型，是政策會累積。

## 七、風險與前提（我要講清楚）

| 風險 | 現在的看法 |
|---|---|
| 門檻值需要逐品牌校準 | 真實成本，但不是架構問題。每次安裝都要校準一次 |
| `safe-zone` 這類啟發式會誤判 | 所以永遠保留 `guidance` 與人手動覆寫的路 |
| 六個部門的目錄要人寫 | 這是主要工作量，不是程式工作量 |
| 你是唯一設計師時，2 小時不夠 | 已記錄：第一階段目標 3–4 小時 |
| 一個 repo 會變大 | 分 `parts/` 目錄，各自的測試獨立 |

## 八、結論

> **這次實驗證明了：策略可以被寫成機器會檢查的條款，而且真的會抓到錯。**
>
> 只要每個部門都照同一個四件套做（目錄、專案、條款、缺口），
> 「一間公司一台機、裝一次跑全部」就不只是願景，是一個可以逐部分驗收的工程計劃。

**下一步不需要再討論架構，需要的是把設計這一塊按四件套重做出來** —— 因為它已經有了全部零件（策略目錄、專案模型、缺口機制），只差把 `mandatory` 檢查器接進去。
