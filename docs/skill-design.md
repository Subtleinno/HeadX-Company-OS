# 一個 skill 的設計：漸進揭露路由

日期：2026-11-03
狀態：設計定案，未實作

---

## 一、為什麼只准一個 skill

你講得很清楚：

> 我限制只用一個 skill，因為我不想搞亂，不想整套東西難用。
> Skill 可以很大，但用漸進揭露（progressive disclosure）的路由方式管理，會好很多，也不會浪費 token。

這個原則我完全同意，而且它解決一個真實問題：

**如果 HxDesign 有 12 個 skill，agent 每次開工都要先判斷「這次該用哪一個」。判斷錯了就做錯事；判斷對了也浪費一次推理。** 一個入口，判斷一次，就不會亂。

---

## 二、一個 skill 不等於一個大檔案

這是關鍵區分。如果「一個 skill」等於「一份三千行的 SKILL.md」，那它每次都會被整份載入，token 全部燒在不相關的段落上。

**正確做法是：一個入口，多份按需要載入的參考。**

```
skill 根目錄（DSH 只會發現這一個）
└── hxdesign/
    ├── SKILL.md          ← 入口兼路由表，硬上限 250 行
    └── references/
        ├── workflow.md   ← 完整生命週期
        ├── create.md     ← Create 的操作與資料模型
        ├── knowledge.md  ← 知識從哪裡來、怎麼挑
        ├── media.md      ← 選圖／選片／素材授權
        ├── brand.md      ← 品牌 DNA 與 tokens
        ├── mcp-verbs.md  ← 六個動詞的細節與錯誤碼
        └── needs.md      ← 何時開單、欄位要求
```

**agent 開工時只讀 `SKILL.md`（約 3k tokens），然後只讀 1 至 2 份相關的 reference（每份 2 至 5k）。**

對比：整份塞進去是 30k 以上，而且大部分與當次任務無關。

## 三、路由要按「動詞」而不是「主題」

這是我從 HxDesign 的 6 個動詞學到的。

如果按主題分類（「品牌」「素材」「專案」），agent 要先想「這件事屬於哪個主題」，再想「怎麼做」——兩次判斷。

如果按動詞分類（「我要 browse」「我要 render」），agent 已經知道自己在做什麼，直接跳到對應段落——一次判斷。

`SKILL.md` 的骨架：

```markdown
# HxDesign

你用六個動詞操作 HxDesign：browse、read、write、find、render、help。
這一頁只做一件事：告訴你「現在該讀哪一份參考」。

## 你要做什麼？

| 你現在的情況 | 讀這一份 |
|---|---|
| 不知道工作區裡有什麼 | references/workflow.md（開頭三節） |
| 要開始一個新專案 | references/create.md |
| 要找品牌的材料或知識 | references/knowledge.md |
| 要挑圖、挑片、挑素材 | references/media.md |
| 要確認品牌規格對不對 | references/brand.md |
| 工具回錯誤碼，不知道怎麼救 | references/mcp-verbs.md |
| 有東西缺，要開一張單給人 | references/needs.md |

## 三條鐵律（不用讀任何參考就要記住）

1. 沒有經 Create，就不是成品。
2. 不要自己判斷「這樣應該可以」——品牌規格在 references/brand.md，去查。
3. 你做不到的，開 Needs，不要假裝做到。
```

## 四、每份 reference 的規矩

| 規矩 | 理由 |
|---|---|
| 第一段必須寫「何時讀我」 | 路由錯了也讓 agent 一眼知道要離開 |
| 硬上限 400 行 | 超過就再拆一層 |
| 一份只講一件事 | 混在一起就無法按需載入 |
| 用例子而非形容詞 | 「這裡要留 48px」比「要留足夠空間」有用 |
| 錯誤碼寫清楚怎麼救 | agent 最需要的是恢復路徑 |

---

## 五、這對 Super Agent 意味著什麼

如果 skill 設計對了，會出現一個很好的效果：

**同一個 skill，資深設計師與新手設計師都用同一份。**

因為它不是「教審美」，是「教操作」。審美來自：

| 來源 | 在哪 |
|---|---|
| 品牌 DNA | HxDesign 的 Material（不是 skill） |
| 設計判斷 | `oil-ui` 技能 + 設計系統文件 |
| 過往決定 | `DECISIONS.md` |

**skill 只負責「怎麼用工具」，不負責「什麼好看」。** 這個分工如果混了，skill 會變成一份永遠不夠長的品味指南。

## 六、範圍修正：現在只服務我們自己

你講得很清楚：

> 我們現在不會做客戶的 iPad app。整個 company-starter 只會先服務我們自己
> （老闆與設計師，一開始老闆也是設計師）。
> 整個系統是為了令公司自動運行；老闆每天只需工作 2 小時，然後 Needs 會派工作給同事。

所以架構由三層縮回**兩層**：

```
┌──────────────────────────────────────────────┐
│  HxDesign（後台）                              │
│  設計師（= 你）+ AI 代理，在 Create 裡工作      │
└───────────────────┬──────────────────────────┘
                    │ MCP + 一個 skill
┌───────────────────▼──────────────────────────┐
│  Company OS（控制台，只有你）                  │
│  批准收件匣 · Needs 派工 · 政策 · 審計          │
└───────────────────┬──────────────────────────┘
                    │ Needs
              ┌─────▼─────┐
              │   同事     │
              └───────────┘
```

**前台（客戶 iPad App）暫時不做。** 之前定的「客戶按確認要老闆批准」保留為**將來**的設計，現在不實作。

## 七、我要老實講一個數字問題

你講「老闆每天只需工作 2 小時」。但現在老闆**同時是設計師**。

那麼這 2 小時要同時做三件事：

| 工作 | 大概需要 |
|---|---|
| 批准收件匣（L2／L3 請求） | 30–45 分鐘 |
| 在 Create 審閱設計、與 AI 改 brief | 60–90 分鐘（如果真的有專案在做） |
| 派 Needs 給同事、驗收交付 | 20–30 分鐘 |

**合計 110–165 分鐘。** 這是樂觀估計，未計意外。

所以我的判斷是：

> **「每日 2 小時」在「你仍是唯一設計師」的階段，數學上很緊。**
> 它真正成立的時間點，是當 AI 代理能自己出到「你只需要審」的稿，而且 Needs 真的把大部分執行工作分出去了。

**這不是壞消息，是校準期望。** 我建議把它寫成兩階段目標：

| 階段 | 目標 | 條件 |
|---|---|---|
| 第一階段（現在） | 每日 3–4 小時 | 你是設計師 + 批准人 |
| 第二階段（有了第二個設計師，或 AI 出稿夠穩） | 每日 2 小時 | 你只做批准與派工 |

**這樣你不會因為「做不到 2 小時」而以為系統失敗。**
