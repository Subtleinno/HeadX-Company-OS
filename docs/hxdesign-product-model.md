# HxDesign 的產品模型：三個介面，一條生命週期

日期：2026-11-03
依據：創辦人口述的原始設計意圖，加上對 `Subtleinno/Hxdesign` HEAD `eb079b6` 程式碼的比對

---

## 一、你講的設計意圖，我重整成這樣

> **HxDesign 是設計師的幕後品牌創作平台。**
> 設計師用 MCP 加**唯一一個 skill** 工作；客戶永遠不登入 HxDesign。

所以它不是一個「工具」，是三個介面組成的系統：

```
┌─────────────────────────────────────────────────────────┐
│ ① 前台：客戶的 iPad / Web App（Canvas）                   │
│    客戶 + AI 代理，用 Canvas 討論出一個有價值的計畫        │
│    ＊ 客戶永遠不登入 HxDesign                              │
│    ＊ 未開始設計（0 code）                                 │
└──────────────────────┬──────────────────────────────────┘
                       │ 計畫成熟後，提交為 brief
┌──────────────────────▼──────────────────────────────────┐
│ ② 後台：HxDesign（設計師 + AI 代理，經 MCP + 一個 skill）  │
│    品牌 identity 材料、知識、Create 成品、brief 改進       │
│    ＊ 建了約 40%，kernel 六件套真做                        │
└──────────────────────┬──────────────────────────────────┘
                       │ 交付、確認、修改
┌──────────────────────▼──────────────────────────────────┐
│ ③ 控制台：Company OS（只有老闆）                          │
│    跨 app 的政策、批准、工單、審計                         │
└─────────────────────────────────────────────────────────┘
```

**關鍵洞察：這三個介面的「信任邊界」完全不同。**

| 介面 | 誰在用 | 可以看到什麼 | 絕對不可以 |
|---|---|---|---|
| 前台 Canvas | 品牌客戶 | 自己品牌的材料與計畫 | 看到其他品牌、改動品牌 DNA |
| 後台 HxDesign | 設計師 | 所有 workspace | 把客戶資料帶到別的 workspace |
| Company OS | 只有老闆 | 全部 | 讓團隊登入（你已定案） |

## 二、為什麼這樣設計是對的（我理解到的理由）

### ① 在 AI 代理時代，設計師的角色變了

你講得很清楚：

> 設計不會再由設計師自己做，而由 AI 代理生成。
> **設計師的工作是預先建立品牌 identity 材料。**
> 然後 AI 代理用這些預製材料與知識，在設計師的指導下生成各種設計與行銷素材。

這代表設計師的價值從「親手做」移到「**建立可被生成的基礎**」。

而這件事只有在**材料是結構化的**時候才成立。所以 HxDesign 才有那條線：

```
Material = Components + Media
Knowledge Raw = 事實 → Knowledge Article = 已加工材料
Create = 成品
```

**它在把「品牌」變成機器可用的原料。** 這才是它的核心資產，不是那些成品。

### ② 客戶不是「下單」，是「跟 AI 討論出計畫」

你說：

> 客戶不是在 app 裡直接提交工作。他們在 app 裡**跟 AI 代理討論**，做出一個有價值的計畫，才提交給設計師。

這解決了接案流程最痛的一件事：**客戶講不清楚自己要什麼。**

傳統做法是設計師花幾輪會議去猜；它把「猜」變成「客戶與 AI 一起想清楚」。

### ③ 為什麼一定要 Canvas，不能只用文字

你的理由很實在：

> 我不要客戶只用文字討論，我要給他們一個 Canvas。
> AI 代理從 Canvas **以視覺接收 prompt**，也在 Canvas 裡回答客戶。
> 客戶可以上傳圖片、影片、任何東西。

**因為一個行銷計畫本來就不是純文字**——它有版面、有情緒、有參考圖、有先後次序。

用文字討論，AI 只能拿到一個摘要；用 Canvas，AI 拿到的是**意圖的完整形狀**。

這也解釋了為什麼 HxDesign 自己寫了一個 canvas 引擎（DOM + 單一 CSS `transform: matrix()`、零 runtime 依賴），而不用 tldraw（授權明文禁止 production use）。

### ④ brief 幾乎就是生成 prompt

你說：

> brief 會用圖表結構化、容易理解，其實它已經接近一個可以直接生成交付物的 project prompt。

**這句話是整個系統的樞紐。** 它意味著：

```
品牌材料 + 知識 + 客戶計畫  →  brief  →  幾乎可以直接生成
                                    ↑
                              設計師在這裡把關與改進
```

設計師不是從零畫，是**改進一個已經很接近成品規格的 brief**，然後與 AI 一起出第一稿。

### ⑤ Needs 是人類介入的接口，兩邊都有

你說 AI 代理會產生 Needs，**給設計師，也給品牌客戶**，兩邊都從各自的 app 收到。

所以 Needs 不是「找不到人時的例外處理」，而是**流程的正式一部分**：AI 做到某一步停下來，開單，人補上，AI 繼續。

## 三、對照程式碼：你的設計意圖，有幾多已經在資料模型裡

這是我覺得最值得講的部分。**它的 schema 已經在等你把前台做出來。**

`create_project.status` 的 CHECK 是四個值：

```sql
CHECK (status IN ('draft','need','exported','delivered'))
```

| 值 | 對應你講的哪一步 | 有沒有 writer |
|---|---|---|
| `draft` | 設計師開始做 | 有 |
| `need` | 等 Needs 補齊 | 有（匯出時發現 gaps） |
| `exported` | brief 已匯出 | 有 |
| **`delivered`** | **設計師提交給客戶** | **沒有任何 code path 寫它** |

**這不是 bug。** 因為「提交給客戶」發生在**前台**，而前台（Track B / Company Hub）還是零 code。

同樣地：
- `apps/web` 有一個 `CreatePreview.jsx`，它的 commit 訊息是
  「a preview is a handover sheet, not a gallery」——**交付單，不是畫廊**。
  這正是你說「設計師 submit the project to Customer」的那個畫面。
- `docs/product/DECISIONS.md` D08 移除批准，正是因為**客戶不在 HxDesign 裡**。
  客戶的「確認」發生在前台，不在後台。

**所以「沒有批准」不是缺口，是邊界。** 我上次的理解要修正：不是「把關移到輸入端的 Keep」那麼抽象，而是更簡單的——**客戶根本不在這個系統裡**。

## 四、這改變了我對界線的看法

### 之前我以為是二分成

```
Company OS（商業真相） ↔ HxDesign（創作真相）
```

### 現在是三層

| 層 | 擁有什麼 | 狀態 |
|---|---|---|
| **前台（Company Hub / Track B）** | 客戶關係、計畫討論、確認與修改請求 | 規格有，code 零 |
| **後台（HxDesign / Track A）** | 品牌材料、知識、成品、brief | 約 40% |
| **控制台（Company OS）** | 政策、批准、跨 app 工單、審計 | 引擎 v0 已通 |

而你之前定「Company OS 只服務老闆」，正好對上：**老闆不需要管客戶的 canvas，只需要管「這件事可不可以做」。**

## 五、創辦人已定案的三件事，以及它們帶來的後果

### 決定 1：Needs 是兩套，完全分開

| | HxDesign 的 Needs | Company OS 的 Needs |
|---|---|---|
| 屬於 | 專案內缺什麼 | 公司層要人做什麼 |
| 誰開 | HxDesign 的 AI（給設計師、給客戶） | Company OS 的 AI（給同事） |
| 誰處理 | 設計師、品牌客戶 | 你指派的人 |
| 在哪裡看 | 後台與前台各自的 app | Company OS 的批准收件匣 |

**後果**：Company OS 不需要接前台的 Needs，也不需要匯總。**兩邊各自完整，互不依賴。** 這令 Company OS 更簡單，也令前台可以獨立開發。

### 決定 2：設計師同時用 AI 代理與 UI

你補充得很清楚：

> 設計師會同時用 AI 代理與 UI 管理專案，因為設計師必須在 **Create** 裡審閱作品。
> **Create 是工作與存放專案的地方。**

所以「一個 skill」不代表「沒有介面」。兩者的分工是：

| | AI 代理（經 MCP + 一個 skill） | UI（Create） |
|---|---|---|
| 做什麼 | 生成、改進 brief、開 Needs、跑渲染 | **審閱**、比較、決定保留哪一版、親手調整 |
| 為什麼 | 它是執行者 | **人必須親眼看到才能判斷** |

**後果**：`apps/web` 的 Create 介面不是過渡產物，是**產品核心**。這也解釋了為什麼 `CreatePreview.jsx` 會被描述成「交付單，不是畫廊」——它同時是工作台與交付介面。

**所以「一個 skill」的定義要精確**：不是「設計師只跟對話框講話」，而是「**agent 需要的全部操作知識，壓縮成一個 skill**」。這才是那條原則的真正意思。

### 決定 3：客戶按「確認」時，要老闆批准

這一條我原本判斷錯了（我以為只需要記錄），你選了「要，而且要老闆批准」。

**後果：Company OS 需要接前台的這一個事件。** 這是目前唯一一條「前台 → Company OS」的線。

設計成這樣：

```
客戶在 Canvas 按「確認完成」
      ↓
前台建立一個請求：project.complete（L2）
      ↓
Company OS 政策閘道判定 → 進批准收件匣
      ↓
老闆批准 → 專案才真正結束
      ↓
拒絕 → 回到前台，客戶與 AI 繼續討論
```

**為什麼這樣設計是合理的**（我想到的理由）：

| 理由 | 說明 |
|---|---|
| **結束一個專案有商業後果** | 通常接著是開票、結案、算設計師的工時。這些不應該由客戶單方面決定。 |
| **它是唯一一個「客戶能觸發老闆」的動作** | 其他客戶行為都不該驚動老闆。只把這一件事放進收件匣，不會造成批准疲勞。 |
| **它給了老闆一個品質的最後閘門** | 若某單做得不好，老闆可以在結案前看到並介入。 |

**如果我的理解有偏差**（例如：其實只要記錄、或者要批准的是「交付」而不是「結案」），你直接講，我改文件。

**新增的動作登錄表條目**：

```json
{
  "id": "hxdesign.project.complete",
  "level": "L2",
  "description": "客戶在 Canvas 確認完成專案；批准後專案才結束"
}
```

## 六、一句話總結我現在的理解

> **HxDesign 是把「品牌」變成機器可用的原料，把客戶的模糊想望變成一份幾乎可以直接生成的 brief；前台負責「想清楚」，後台負責「做得到」，人類在兩邊用各自獨立的 Needs 補上 AI 做不到的事，而「一個專案算不算完成」最終由老闆簽。**

這比我上次講的「定義什麼算成品」更準確——因為**成品不是終點，brief 才是真正的產品；而結案是老闆的權力。**
