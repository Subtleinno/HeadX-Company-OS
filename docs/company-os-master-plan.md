# AI 原生公司總規劃(Company OS Master Plan)
版本:v0.4 草案|日期:2026-11-03|負責人:創辦人(唯一批准人)
本次修訂(v0.4):加入介面標準(Apple HIG、白底黑 accent、禁 emoji)、每 app 必備 MCP、
ERPNext/WordPress 部署策略(見原則 9–10、ADR-015 至 ADR-017、`docs/company-os-design-system.md`)

## 1. 目標
由 Super Agent 與多個專職 AI Agent 持續營運與開發公司,創辦人每天約 2 小時處理「批准收件匣」。
這是漸進目標,不是第一天的狀態。初期每日審批時間預計會超過 2 小時,隨規則與紀錄成熟而下降。

## 2. 不可違反的原則
1. 責任在人:香港目前沒有法律框架可委任 AI 為董事;董事轉授權力需有授權依據,並須持續監督。請公司秘書/律師確認章程授權範圍。
2. 風險分級:批准與否按「動作」分級,不按 Agent 分級。
3. 預設拒絕:逾時未批准即取消,不自動執行。
4. 最小權限:每個 Agent、每個品牌各用獨立帳號與金鑰,權限只含其任務所需。
5. 不可變日誌:所有寫入操作、批准與拒絕都記錄,Agent 無權修改日誌、權限或金鑰。
6. 策略庫保密:HxDesign 的內容策略不得出現在客戶端 API、日誌、第三方插件或送往外部模型的非必要內容中。
7. 財務分權:Agent 可建草稿,過帳、付款、退款由人批准(或經人預先批准的明確規則)。
8. 隨時可停:全域熔斷開關,可一鍵暫停所有 Agent 的寫入。
9. **AI 原生:每個 app 必須提供 MCP 伺服器**,採用最新 MCP 規範,令 Agent 能以結構化方式使用;但 MCP **不得**提供「批准」工具,批准永遠只經人(見 ADR-016)。
10. **介面標準:Apple HIG + 白底黑 accent + 禁止 emoji**(見 ADR-015 與 `docs/company-os-design-system.md`)。

## 3. 風險分級
| 級別 | 例子 | 控制 |
|---|---|---|
| L0 唯讀 | 查報表、情報研究、對帳 | 自動,記錄日誌 |
| L1 草稿/可還原內部寫入 | 內容草稿、分錄草稿、採購單草稿、開 PR | 自動執行並通知,事後抽查 |
| L2 對外或有財務影響 | 發布貼文、向供應商下單、發信客戶、退款 | 執行前批准;或在人預先批准的規則內自動 |
| L3 破壞性/權限相關 | 合併 PR、部署正式環境、刪資料、過帳大額 | 指定批准人,可要求第二審核 |
| L4 禁止 | 關閉日誌、改自己權限、取用金鑰 | 閘道直接擋下,無批准路徑 |

新動作一律從 L2 起步;累積足夠紀錄、你從未修改過,才可討論降級。

## 4. 目標架構(分層)
1. 控制中心:DeepSeek Harness(DSH)+ dsh-superagent-prototype,於 Docker 運行。每個品牌/每條線一個容器,各自獨立金鑰。
2. 政策閘道(自建):所有 Agent 對外部系統的寫入必經此層,負責分級、金額上限、白名單、冪等鍵、日誌。
3. 批准收件匣(自建):彙整 L2 以上請求為每日摘要,附依據、金額、影響、一鍵批准/退回(結構化理由代碼)。
4. HxDesign:品牌 DNA、素材、知識、策略、元件庫、Create;透過 MCP 供設計師端 Agent 使用。
5. 營運層(待定,見第 8 節):訂單、庫存、採購、物流。
6. 會計:ERPNext(Frappe Cloud 官方託管)只做總帳;經「會計轉接器」把已確認的交易推為草稿分錄。
7. 網站:WordPress.com 只作內容網站。
8. 通知:飛書(最後接入)。

## 5. 兩條 Agent 線
- 開發線:想法 → issue → Worker 在獨立目錄開發 → 測試 → PR → 人批准合併。對象為 HxDesign、政策閘道、收件匣、營運層、轉接器等自家 repo。
- 生產線:每日情報 → 計劃 → HxDesign Create → 缺資料開 Needs → 員工補件 → 製作 → 監修 → 批准發布。

## 6. 官方 Super-agent 的已知限制
- dsh-superagent-prototype 是研究原型,非官方產品;針對單一 GitHub repo 的主動式 coding agent。
- 目前接收來源為 GitHub 與可選的飛書;文章中的多信道等設計尚未全部實作。
- 官方實驗只用合成負載,不代表長期自治已可靠。
- DSH 原生審批只有「詢問/不詢問」兩種,按金額或風險分級要自建。
- 社群 Docker 映像預設為單人、受信任的開發環境,不是多租戶沙箱;品牌之間要用容器隔離。

## 7. 階段計劃
| 階段 | 內容 | 完成條件 |
|---|---|---|
| P0 | 建置 Super Agent(見 bootstrap 任務書) | 在測試 repo 跑通 issue→PR;審批預設拒絕驗證通過;熔斷開關可用。首個真實任務 = 政策閘道模組 |
| P1 | 開發線自舉:Agent 開發政策閘道、批准收件匣 MVP、日誌 | 兩者通過測試並由你批准合併 |
| P2 | 開發線擴展到 HxDesign(先測試 fork,再正式 repo,僅限 PR) | 連續數週 PR 品質穩定 |
| P3 | 生產線:內容與行銷(每日研究、Needs、發布前批准) | 審批紀錄可量度(耗時、修改率、推翻率) |
| P4 | 營運層與 ERP 原型(訂單集單,只產生草稿) | 每日對帳零差異 |
| P5 | 會計轉接器 + ERPNext(Frappe Cloud 試用) | 會計師審過科目表與流程 |
| P6 | WordPress.com 網站發布、飛書通知 | 發布前批准流程正常 |
| P7 | 依紀錄逐步放寬低風險類別 | 每次放寬都有書面理由 |

## 8. 待決定事項(Open decisions)
1. 營運層引擎:Medusa、其他,或自建 TypeScript 服務。(ERP 邏輯應與商務引擎解耦,日後可搬遷。)
2. POS:是否必須實體門市即時收銀;Medusa 沒有內建 POS。
3. 各品牌是否為獨立公司(影響會計訂閱/公司數量與 ERPNext 多公司設定)。
4. 香港本地化:ERPNext 的科目表、報表是否符合會計師要求(尚未查證)。
5. 策略庫存放:Agent 是否可讀取內容,或只讀結構。
6. 社群 MCP/插件(如 Frappe Assistant Core,AGPL-3.0)能否在 Frappe Cloud 上使用,需向官方確認。
7. 公司章程對授權的規定(律師/公司秘書)。
8. PIM(產品資料管理):**暫緩**。現時未有產品,資料模型只保留「產品資料」位置,不設計 PIM。待 P4 有實際 SKU 量時再決定(合併入 ERP/獨立 PIM/自建)。
9. 外置渲染機的連接細節:內網地址、認證方式、ComfyUI API 端點、HyperFrames 是否同樣在該機、佇列與失敗重試機制。
10. ERPNext 容器化的維護方案:自架 Frappe 官方映像,或在試用期先用 Frappe Cloud;須與會計師確認後再定。
11. 各訂閱服務(Perplexity 等)的使用條款是否允許瀏覽器代操;須逐個查閱並記錄結論。

## 9. 指標
- 每日審批時間、請求數、平均閱讀時間。
- 推翻率與修改率(過低可能代表批准疲勞或閘門多餘)。
- 對帳差異、失敗/重試次數。
- 每日 token 成本與上限觸發次數。
- 每週隨機抽查自動通過項目的結果。

## 10. 風險清單
- 批准疲勞導致監督失效 → 分級、批次、抽查。
- Agent 越權或提示詞注入 → 最小權限、閘道、L4 禁止。
- 財務邏輯錯誤 → 規格先於程式碼、不可變帳目、冪等、每日對帳、會計師審核。
- 供應鏈風險(第三方插件) → 逐一審查、鎖版本、容器隔離。
- 成本失控 → 每日用量上限、熔斷。

## 附錄 A:架構決策記錄(ADR)

本附錄記錄 2026-11-03 完成 P0 Step A 後,由創辦人與 DSH 討論並定案的決策。
目的是讓日後接手的人(包括未來的 Agent)可以追溯「為何當初這樣選擇」。

### ADR-001:定位 — 先內部使用,但保留產品化路徑
- **決策**:Company OS 現階段只供創辦人旗下公司使用,不建多租戶、授權、計費。
- **保留**:所有公司專屬設定集中於單一 company.config(公司識別、品牌清單、科目表映射),不寫死於程式各處。
- **理由**:「每間公司一個開始套裝」是長期願景,但多租戶設計會令前期成本增加 3–5 倍,且需求尚未確認。
- **代價**:日後轉為產品時需一輪外部化改造;屆時只需改動設定層與資料邊界,不需重寫業務邏輯。
- **狀態**:已定案(可於 P3 後重新評估)。

### ADR-002:公司與品牌 — 一間公司,多個品牌
- **決策**:以一間法人公司承載多個品牌;會計走一套總帳(ERPNext 單一 company),以「品牌」作為分析維度。
- **要求**:即使同屬一間公司,**品牌之間的資料仍須隔離**(每個品牌獨立帳號與金鑰,不得互相讀取),與第 2 節原則 4 一致。
- **資料模型**:所有業務資料由第一日起帶 rand_id,查詢一律經品牌過濾。
- **理由**:架構較簡單;品牌日後若要分拆成獨立公司,資料已經按品牌分開,遷移成本低。
- **狀態**:已定案。待決定事項第 3 項(各品牌是否獨立公司)降級為「日後按稅務/業務需要再議」。

### ADR-003:系統邊界 — 引擎只連接,不合併
- **決策**:Company OS 是「引擎層」,只負責政策閘道、批准收件匣、審計日誌、風險分級、熔斷開關、Super Agent。各業務系統為獨立服務,經 API 連接,不併入 Company OS 程式碼庫。
- **範圍**:HxDesign(品牌/知識庫/設計)、AI Native ERP(營運)、ERPNext(只做會計)、WordPress(網站),將來可能的電商。
- **理由**:避免單一系統故障拖垮全部;換供應商(例如換走 WordPress)時不需改動引擎;團隊可按需分拆。
- **狀態**:已定案。

### ADR-004:Super Agent 範圍 — 可服務所有公司 repo,但分開發線
- **決策**:一個 Super Agent 可開發所有自家 repo,但每條開發線(company-os、HxDesign、ERP 等)使用獨立金鑰與獨立工作目錄。
- **理由**:一個大權限的 Agent 一旦出錯或被提示詞注入,可同時破壞多個 repo。分線 = 最多只壞一條。
- **待查證**:官方 dsh-superagent-prototype 是否支援多 repo。若不支援,則每條線跑一個實例(見 Step 4)。
- **狀態**:已定案;實作方式待 Step 4 查證。

### ADR-005:首個真實使用場景 — Agent 開發政策閘道模組
- **決策**:P0 驗收完成後,第一個真實任務是由 Agent 開發「政策閘道」模組,而非內容創作線。
- **理由**:先建立閘道與批准機制,再開放其他自動化,否則 Agent 可在沒有任何攔截的情況下直接對外發布。
- **狀態**:已定案。

### ADR-006:PIM 暫緩
- **決策**:現時未有實體產品,不設計 PIM。ERP 資料模型只保留「產品資料」擴充位置,不在程式內寫死產品結構。
- **觸發條件**:P4 起有實際 SKU 量(建議門檻:超過 100 個 SKU,或多語言/多通路的產品內容需要管理)時,重新評估三條路:合併入 ERP / 採用獨立 PIM(如 Akeneo)/ 自建。
- **狀態**:已定案,列為第 8 節待決定事項之 8。

### ADR-007:開發節奏 — 穩
- **決策**:每個模組按「設計 → 實作 → 測試 → PR → 創辦人批准」完成,不做為求速度而跳過測試的推進。
- **預計時程**:P1 引擎(日誌、分級、閘道、收件匣、銜接、指標)約 6–9 個月。
- **理由**:創辦人不能承受資料遺失或審批紀錄不完整;「每日 2 小時審批」的終極目標依賴可信的紀錄與分級,而非更快的產出。
- **狀態**:已定案。

### ADR-008:Needs 系統 — Agent 與人的交接機制
- **決策**:凡是 Agent 無法自行完成的工作(影片、實拍照片、實物設計、需要簽署或蓋章的文件等),Agent 不得停下來等人發現,必須自動建立一張 **Need**(工單)。
- **Need 的必填欄位**:品牌、類型(影片/照片/設計/文案/其他)、為何需要、期望產出規格、用途(哪個 app、哪次發布)、截止時間、Agent 已嘗試過什麼、參考資料連結。
- **生命週期**:建立 → 出現在 Dashboard 與每日摘要 → 指派或自動按技能配對給員工 → 員工交付(檔案 + 說明)→ Agent 驗收(是否符合規格)→ 沿用或退回 → 完整記錄在審計日誌。
- **強制欄位「Agent 已嘗試過什麼」**:避免 Agent 未嘗試就開單;也讓人知道從哪裡接手。
- **回饋迴路**:Need 關閉後,Agent 必須記錄「這類工作未來能否自動化」,成為 Super Agent 自動升級的輸入。
- **理由**:傳統自動化在能力邊界處失敗即停,創辦人無法預知缺口;Needs 把「失敗」轉為「可執行的工作單」,讓系統可持續運作。
- **狀態**:已定案,列為 P1 核心模組。

### ADR-009:Company Dashboard — 單一全景介面
- **決策**:建立一個 Dashboard,以「公司 → 品牌 → App」為主軸,同時顯示:
  1. **組織層**:所有公司、品牌、App 的清單與健康狀態;待批事項;未完成 Needs;每品牌成本與產出。
  2. **平台層**:DSH 本身的狀態 — 模型路由、已安裝 Skills、Plugins、MCP 伺服器、記憶空間、可用工具清單、版本相容性。
  3. **營運層**:Super Agent 各開發線的進度、PR 佇列、失敗重試、熔斷狀態。
- **實作位置**:以 `dsh-better-sidebar` 的第三方 tab 註冊機制嵌入 DSH 側欄,不必另開瀏覽器視窗;資料一律唯讀,寫入動作仍必經政策閘道。
- **理由**:創辦人不是技術人員,必須用一個畫面掌握「這部機器現在在做什麼、卡在哪裡」,才能維持監督;分散在多個工具會造成批准疲勞。
- **狀態**:已定案,列為 P1-D 之後的主要里程碑。

### ADR-010:Docker 統一承載 — 所有 App 皆容器化
- **決策**:所有 app(含第三方系統)一律以 Docker 容器在本機運行,包括 Company OS 自建服務(閘道、收件匣、Dashboard)、HxDesign、AI Native ERP、ERPNext、WordPress,以及將來可能的電商。
- **統一標準**(每個容器都必須符合):非 root 使用者、根檔案系統盡量唯讀、只掛載專用工作目錄、明確 CPU/記憶體上限、預設不對外開放埠(只綁 127.0.0.1)、不掛載 Docker socket、獨立網路、獨立資料卷、每日備份。
- **理由**:一個 app 出事不會拖累全部;換版本可回滾;備份與遷移一致;亦對應 master plan 第 2 節原則 4 與第 6 章的容器隔離要求。
- **代價**:ERPNext 容器化與升級較複雜(需自行維護 Frappe 官方映像),須預留時間與備份方案;若某階段時間壓力過大,可先在 Frappe Cloud 試用,但最終仍以自架容器為準。
- **狀態**:已定案。

### ADR-011:外置渲染與創作機器
- **決策**:重 GPU 或重運算的工作不放在主機。
  - **圖像生成**:專用機器上的 ComfyUI(已安裝 Qwen Image 2.1),經區網 API 呼叫。
  - **動效與影片**:HyperFrames,供社交媒體動態內容與 Agent 自行剪輯使用。
  - **設計品質**:Open Design + Taste Skill v2,作為設計產出的檢查與風格把關。
- **連接方式**:主機的 Agent 只透過 HTTP API 呼叫該機,不把模型或素材庫複製到主機;素材仍以 HxDesign 為唯一真實來源。
- **理由**:主機要保持輕量與穩定;GPU 工作隨時可以中斷重跑,失敗成本低。
- **待確認**:該機的內網地址、認證方式、API 端點、可用佇列機制(見第 8 節待決定事項 9)。
- **狀態**:已定案,具體連線待 P2 實作時確認。

### ADR-012:研究與模型策略 — 瀏覽器代操,不破解 API
- **決策**:Perplexity 與其他有訂閱但無官方 API 的服務,一律以 **GUI 瀏覽器代操**方式使用(透過 `dsh-browser` 操作已登入的瀏覽器),不嘗試把它們的訂閱轉為 API、不輸入或儲存帳戶密碼、不繞過任何登入或使用條款。
- **規則**:
  1. Agent 只操作已經由使用者本人登入的瀏覽器工作階段,不代為輸入密碼、OTP 或兩步驟驗證碼。
  2. 每次操作前後記錄:哪個服務、哪個任務、產出什麼;不把整頁 HTML、cookie 或登入憑證寫入日誌。
  3. 若服務條款明確禁止自動化,該服務列為「人手上使用」,Agent 不代操。
  4. 需要大量重複研究時,優先使用有官方 API 的服務(例如 DeepSeek、Claude API),以穩定性和合規性換取速度。
- **理由**:短期省成本與快速取得高階模型能力;但代操瀏覽器本質上脆弱(介面改版即失效),且存在帳戶風險,因此必須明文設限。
- **狀態**:已定案。

### ADR-013:閘道開發方向 — 先評估開源,再 fork 改造
- **決策**:不自零編寫政策閘道。先評估社群現成方案(候選:`dsh-permission-rules`、`dsh-auto-mode`、`dsh-approval-gate`),選最接近者 fork 改造,只自建它們欠缺的部分(金額上限、冪等鍵、品牌隔離、Needs 觸發)。
- **附帶要求**:fork 必須保留上游授權聲明、記錄 fork 的 commit、建立同步上游的流程,並對所選方案做一次安全審查(供應鏈風險)。
- **理由**:可節省約 2–4 個月;但必須避免「黑盒依賴」——凡引入第三方核心程式碼,都要能解釋它為什麼擋得住。
- **狀態**:已定案;具體選型於 P1 第一至二週產出評估報告後拍板。

### ADR-014:DSH 插件策略 — 能力優先,逐個審查
- **決策**:為避免工作受阻,優先安裝能消除「能力缺口」的插件(瀏覽器操作、視覺、記憶、多 Agent、介面工作台、技能與 MCP 管理、插件市場)。
- **規則**:
  1. 只安裝有官方 npm 套件者;純 GitHub 專案須先審查源碼才可安裝。
  2. 安裝前核對套件名與作者,避免同名劫持(生態中存在同名但不同作者的套件)。
  3. 明文禁止:繞過沙箱、全自動批准、管理員權限檔、對外開放公網、破解或越獄類插件。
  4. 每次安裝後記錄版本、來源、用途於附錄 B;上游不相容即回滾。
- **已安裝基準(P0,2026-11-03)**:`dshmarket` 1.73.7、`dsh-browser` 0.1.0、`dsh-better-sidebar` 0.28.2、`dsh-skill-mcp-panel` 2.3.5、`dsh-mnemon` 0.5.38、`@liustack/modlens` 3.27.2、`@nanmicoder/dsh-agent-teams` 0.1.28。
- **狀態**:已定案。

### ADR-015:UI/UX 標準 — Apple HIG + 白底黑 accent
- **決策**:Company OS 及其所有子系統的介面一律以 **Apple Human Interface Guidelines** 為規則基礎;配色固定 **白底(#FFFFFF)+ 黑主色(#000000)**;**全面禁止 emoji**(介面、文件、提交訊息、註解);動效使用 **GSAP**,時長 120–320ms,並尊重 reduced-motion。
- **可控制設計系統**:結構規則(間距、對比、動效、可及性)全系統統一;品牌層可經 `brand.config` 換色與字型,**制度統一、皮膚可換**。
- **指引來源**:DSH 已安裝 `apple-hig-mcp`(MCP 伺服器,提供 Apple HIG 即時查詢);公司自訂規格見 `docs/company-os-design-system.md`。
- **理由**:創辦人不能忍受不一致、吵雜或「AI 味」的介面;白底黑 accent 是最耐看、最不易出錯的選擇,也讓狀態必須以結構(字重、位置、圖示)表達而非顏色,對色盲使用者更友善。
- **狀態**:已定案。

### ADR-016:AI 原生 — 每個 App 必須提供 MCP
- **決策**:每一個 app(自家開發與接入的第三方)都必須提供一個 **MCP 伺服器**,採用最新 MCP 規範,令 AI Agent 能以結構化方式使用該 app,而不必爬網頁或模擬點擊。
- **規則**:
  1. MCP 與 UI 共用同一個核心服務層,不另寫一套邏輯。
  2. MCP 工具必須有型別化參數、幂等鍵、結構化回傳(含 `request_id` 對應審計日誌)、明確錯誤碼。
  3. **MCP 不得提供「批准」或「撤銷批准」工具** — 批准永遠只經人在 UI 上完成。
  4. Company Dashboard 必須提供 `dashboard.snapshot`,讓 Super Agent 讀取公司現況。
- **理由**:這是「系統自己成長」的前提 — Agent 要能操作系統,才能發現缺口並修補;但同時必須有一條無法被繞過的人類批准路徑。
- **狀態**:已定案,寫入 master plan 第 2 節成為原則 9。

### ADR-017:ERPNext 與 WordPress — 開發用容器,生產用 SaaS
- **決策**:
  - **ERPNext**:開發與測試期用 Docker;正式上線後改用 **Frappe Cloud 官方託管**(只做總帳)。目的:開發可隨意試錯,生產有備份、有支援、免自行升級。
  - **WordPress**:**維持外部 SaaS(WordPress.com)**,Company OS 只經 API/MCP 接駁,不自行架設。原因:自架 WordPress 需要 CDN、物件快取、調校與持續安全更新,等於營運一台主機;容器化不會令它更安全,只會令人誤以為安全。
- **例外**:若日後出現明確需求(例如需要完全自訂外掛或深度整合),再以 ADR 方式重新評估。
- **理由**:創辦人的目標是營運公司,不是維護伺服器;引擎只連接、不合併(ADR-003)。
- **狀態**:WordPress 部分由創辦人決定「連接時再議」;ERPNext 部分已定案。
