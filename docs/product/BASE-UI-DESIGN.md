# Base 共用介面與底座管理設計

日期：2026-11-06
狀態：設計方向紀錄，未實作；不是可直接開工的完整施工規格。

## 1. 目的與範圍

先完成 Base：將現有後端底座接成可使用的 UI，不重造底座。Base 包括共用操作外殼，以及透過 Boss portal 使用現有底座的管理介面。後端能力屬 platform、管理畫面放 Boss portal，兩者不矛盾。Boss portal 不另建身份、授權、組織或設定的資料副本。

本輪不做策略、招式庫、Needs 業務流程、成效 dashboard、Marketing Design 或其他部門業務功能。不因補 UI 順手開發未有的業務能力。

## 2. 文字參考與已確認方向

介面參考老闆在討論中展示的 Hxdesign 外殼，不依賴讀者取得截圖。參考的是操作結構及視覺，不代表搬用 Hxdesign 後端或受其產品範圍限制。

桌面畫面由上至下為：第一行全局頂欄、第二行子選單／操作列、下方左側工作欄與右側主內容區。外殼佔滿視窗，不採用置中的 dashboard 卡片網格作主要結構。

第一行由左至右為：側欄開關、app 選擇器、品牌／工作範圍選擇器、目前 app 的主選單，右側為全局工具及帳戶。app 選擇器必須在品牌選擇器左邊，Boss portal 與部門 app 從同一個 app 選擇器進入。切換 app 後，主選單、第二行、工作欄與主內容隨之切換；共用外殼位置保持一致。

第二行顯示目前主頁的子頁或上下文操作，不重複第一行 app 主選單。左側工作欄提供當前頁面需要的工作索引，不永久塞滿所有 app 的功能。沒有工作索引時不製造假清單。主內容由第二行下方開始，在工作欄右邊靠左排列，保留足夠留白，不以假統計填滿空間。

## 3. 外觀

支援白色與深色模式。老闆日常用白色模式，因此原型及主要驗收先以白色模式為基準；深色使用相同結構與操作，不另起一套頁面。

白色模式：白色主畫布、極淺灰工作欄、深色正文、灰色輔助字、細線分隔。深色模式：近黑主畫布、略亮的工作欄與浮層、淺色正文、灰色輔助字。選中項目須清楚可辨，不能只靠顏色。沿用系統字體、克制圓角、平鋪內容；浮層可用柔和陰影，綠色 #B8F36B 只作點綴，不用 emoji 或紫色漸層。

主題色、字體、間距、邊框與元件樣式集中管理，app 不各自複製。既有來源以 docs/INDEX.md 所列 packages/design-tokens、packages/ui-kit 為核對起點，未核實實作前不宣稱已具備雙主題。

## 4. 名稱可改，身份穩定

產品顯示名稱、各 app 顯示名稱、主選單及子選單名稱必須容易修改，不可散落硬編碼於多個畫面。顯示文字與穩定識別字分開：改名不得更改 app ID、資料關聯、授權關聯、路由或選單穩定 key。

已核實 apps/boss/manifest.json 分開定義 id=boss、title=老闆台、route=/boss，available=false。app 名稱以既有 manifest／registry 為起點，不另造第二份 app 清單；不因寫設計文件便將 available 改為 true。

產品名稱、選單標籤、語言文字與未來可選的自訂名稱，須在施工前定義各自唯一來源、覆寫優先次序及缺值回退。不得用語言文字作路由或授權 key。顯示名稱可改不等於本輪已承諾提供所有改名的管理表單；設定入口與儲存方式仍待核對。

## 5. 入口與頁面歸屬

共用外殼：app 切換、品牌／範圍切換、導航、明暗模式及共用狀態。

個人帳戶選單：自己的帳戶、安全設定、外觀偏好及登出；只接已核實能力。

Boss portal → 管理：公司設定、品牌與組織、員工與 agent、app 授權。管理頁屬本輪 Base，不必等待 Boss portal 業務功能。建議管理區子選單為「公司設定／品牌與組織／員工與 agent／App 授權／系統與紀錄」；精確命名與分頁仍是設計草案。

app 選擇器回答「我可以使用甚麼 app」，不是授權管理入口。Boss portal 的 App 授權頁回答「誰可以使用甚麼 app」。兩者共用後端事實，不以隱藏選單代替後端授權檢查。批准仍只能由人操作，敏感授權與設定變更遵守既有政策及審計，不在本文件重定義權限。

## 6. 現有能力與接駁核對

截至本文件，已讀 AGENTS.md、docs/INDEX.md、apps/platform/src/server.ts、apps/platform/src/app.ts、apps/boss/manifest.json。這是原始碼閱讀，不是執行驗收。

server.ts 已註冊 auth、staff、agents、modules、settings、org、grants、files。其註解指出員工與 agent 身份、公司設定與組織管理要老闆使用；授權註冊涵蓋申請、批准、拒絕、撤銷、查詢及存取檢查。各路由檔、欄位、錯誤碼及測試尚未逐項核對，不憑註冊或目錄存在推斷完整 UI 合約。

接駁清單：
- 登入與個人帳戶：核對首次設定、登入、登出、安全操作及 session 失效行為。
- 公司設定：核對可讀寫欄位、驗證與保存結果。
- 品牌與組織：沿用 org_unit／org_unit_edge，核對品牌表達、層級及設定繼承，不複製 Hxdesign workspace 資料模型。
- 員工與 agent：分清身份類型、可用操作、狀態及權限。
- App 授權：分清已註冊、可用、獲授權及拒絕原因。
- 檔案：核對上傳、清單、下載、軟刪除、限制及可見範圍；不為有檔案 API 就另造素材業務 app。
- 審計、備份、背景工作、資料庫帳號工具：先查明是否有安全的讀取／操作介面，不把資料表、worker 或命令列工具當成已可從瀏覽器操作。

app.ts 已定義 /livez（進程存活）、/health（資料庫及儲存依賴）、/health/storage（更具體儲存診斷）。UI 應分別呈現，不把進程存活寫成整套系統正常；診斷不可用或讀取失敗要明示，不顯示假綠燈。

## 7. 互動與狀態

每頁須定義載入、有資料、空資料、無權限、失敗與重試；表單須有未修改、未保存、保存中、成功與失敗狀態。失敗不能偽裝成空資料或已保存。不得顯示虛構 KPI、品牌、員工、授權或成功紀錄。

品牌選擇器是工作範圍，不是每頁必須屬於單一品牌。全公司設定要明示全公司，避免頂欄品牌造成錯誤暗示。建議 Boss portal 支援全公司／全部品牌與單一品牌範圍；切 app 盡量保留相容範圍，不支援時先提示。這些範圍切換細節待後端核對，不能據此新增越權查詢。

切 app、品牌或頁面遇到未保存修改時，建議提供留下、放棄修改後離開的選擇，不靜默丟失內容。重整與深連結須能辨認目前 app、範圍及頁面；實際路由方案待設計。桌面精確尺寸、窄螢幕收合、鍵盤操作、焦點與無障礙標示須在施工前補齊，不能只按截圖比例猜定。

## 8. 下一步與完成判準

先逐項讀相關路由、資料型別及測試，建立畫面／欄位／操作／來源／限制／缺口對照；再做可切 app 與明暗模式的外殼原型。之後才按已核實能力拆施工 issue，一次一張。未知的 API、權限及版面細節要顯式列明，不由實作者猜。

Base UI 完成須有真實後端接駁、狀態與失敗處理、權限驗證、名稱變更不破壞識別及路由的測試，以及實際驗收證據。設計文件合併不代表 UI 完成。唯讀鏡像 repo 在老闆確認完成相關基線後另行處理，本輪不建立。

## 9. Agent-first 與設定介面補充（2026-11-06 19:20 共識）

### 9.1 工作以 agent 為主，設定必須可見

Company OS 永遠以 AI Native 為前提。使用者主要與自己的外部 AI agent 對話，agent 經 MCP 操作；系統保存事實、執行規則、管理授權並留紀錄，不在 repo 執行 AI 模型。

工作／創作的 UI 主要用來預覽、檢視、有限 CRUD、人工決策及必要接管，不重建傳統逐步手動工作 app。這是未來工作介面的方向，不在本輪開發部門或創作功能。

系統設定／管理則必須有完整、容易發現、容易理解、可直接操作的管理頁，不能因 Agent-first 而省略。使用者不應先知道設定存在，再向 AI 問出來。Agent-first 不等於 settings-hidden；有限 CRUD 不得解讀為削減底座管理介面。

後端管理能力仍須逐項核對並接入 UI，但按使用者目的組織，不把每個 API 機械地變成一張表單。人與 agent 的入口不同，仍須共用後端事實及規則，不在前端另存業務資料副本。

### 9.2 設定頁 UX 要求

每項設定必須交代用途及位置、目前值、影響範圍、保存方式與生效時機，以及不可修改或失敗的原因與下一步。如有繼承，顯示來源及本層是否覆寫；不假定所有設定都有繼承。

按任務分組，不照資料表或程式目錄名堆欄位。設計應支援由員工身份查看相關 app 授權，亦由 app 角度檢視授權對象；兩種視角共用同一份資料，具體 API 支援仍待核對。個人帳戶與公司管理分開；全公司設定不可被頂欄品牌誤導為只影響該品牌。

保留第七節所有載入、空資料、無權限、未保存、保存中、成功與失敗處理，不以空白掩飾錯誤，不以成功提示掩飾未保存。

### 9.3 MCP 與連線需求

外部 agent 應可從本機或經網絡連入；遠端部署包括 Cloudflare Tunnel 及只可經 VPN 的環境，不強迫每間公司開公開入口。這是產品要求，不是已實作聲明；傳輸方式、入口分類、認證、客戶端相容性及版本差異須先核對，不能直接公開 internal gateway 或繞過既有暴露限制。

網絡可達不等於資源獲授權。沿用固定六個動詞 browse/read/write/find/render/help；MCP 沒有 approve 工具，批准由人按；對外訊息經發件箱政策。不得把敏感批准變成普通 CRUD 讓 agent 直接改為已批准。

MCP 是底座架構前提及需要核對的接入能力，本次文件修訂不授權整套 MCP 實作。連線狀態及管理畫面仍待設計，不顯示虛構的已連接狀態。

### 9.4 補充未決與核對方式

老闆偏好白色是主要設計基準，不自動等同所有使用者的預設偏好。主題保存、是否跟隨系統、頂欄擠壓及側欄無索引時收起方式均待定。截圖右側工具的具體功能亦待核對，不把每個圖示當成已批准範圍。先前卡片 dashboard 原型不作本設計基準。

下一輪核對表擴充為：底座能力 → 人的設定 UI → agent/MCP 操作需求 → API／來源 → 影響範圍與權限 → 狀態及失敗 → 缺口。不得以 Agent-first 作為省略設定頁的理由，亦不得將文件方向當成 UI 或 MCP 已完成。
