# 跨機多公司入口｜概念與設計底稿

日期：2026-11-09
狀態：概念討論，**未經決定、未授權施工**。唔改 C01／C24／MASTER-PLAN §236，唔改任何程式。
來源：Billy「we didn't think this before」＋ `DECISIONS.md` C01／C24／C41–C51、`MASTER-PLAN.md` §12、`BASE-UI-DESIGN.md` §9.3、`WORKSPACE-APP-SCOPE-DESIGN.md`。

## 1. 先拆開三種「方便」

「一次登入多台機」其實包住三個唔同要求，混埋一齊就会做錯嘢：

| | 想解決乜 | 性質 | 可唔可以做 |
|---|---|---|---|
| (a) | 唔想記兩組密碼、唔想登入兩次 | 身份／憑證 | 可以做，但唔等於合併授權 |
| (b) | 唔想開兩個網址／兩個瀏覽器 | 入口／目錄 | 可以做，純導覽 |
| (c) | 想喺一個畫面睇晒兩間公司嘅數 | 資料合併 | **唔應該用 UI 捷徑做**，撞 C01／C24／§236 |

(a)(b) 係入口層；(c) 係資料層。前兩者解決咗，老闆已經唔使「搵」兩部機，但仍然係兩間公司。

## 2. 而家嘅隔離唔係技術債，係資產

- C01：一機一公司；香港／大陸各一份，帳戶分開；兩機**冇跨機連線**；公司間往來當兩間公司交易，經發件箱用 Email 傳單據。
- C24：大陸資料留喺大陸機；任何境外存取（包括 VPN）法律責任喺公司；兩部機唔建立跨境連線。
- §236：各有老闆、員工、brand、DB、MinIO；版本係安裝時揀，唔依機器位置自動決定。
- BASE §9.3：網絡可達 **唔等於** 資源獲授權；唔好公開 internal gateway。

推論：兩組憑證分開，一次外洩只爆一間；一組中央 SSO，一次外洩爆兩間，而且大陸機要長期連到外部 IdP，直接同「不建立跨境連線」衝突。
**目標應該係「減低切換成本，但保留隔離邊界」，唔係「消除邊界」。**

## 3. 四件唔應該做嘅事

1. **頂欄「公司切換器」** — 會令人以為資料可以跨機撈；同「一機一公司」矛盾，亦係「假範圍」。
2. **中央雲端 IdP／SSO** — 大陸機可達性、法律責任、單點故障、單點外洩；亦要改 C01。
3. **跨機即時 API 連線／合併報表** — C01 已定公司間往來行發件箱，唔係即時查詢。
4. **自動同步員工／角色／品牌** — 同一個人喺兩間公司可以係老闆 vs 只係 viewer；角色係**本機授予**，唔應該跟人跨機複製。

## 4. 建議模型：統一「人同佢嘅 agent」，唔係統一「資料庫」

呼應 `BASE-UI-DESIGN.md` §9 Agent-first：使用者自帶外部 AI agent，agent 經 MCP 各自連每部機。人可以帶住同一個身份去兩部機，但每部機各自決定「呢個係邊個、有乜權」。

三層必須分開，唔可以一張表攪埋：

| 層 | 答嘅問題 | 唯一來源 | 放喺邊 |
|---|---|---|---|
| 身份 Identity | 呢個係咪同一個人 | 使用者自己嘅 key／Passport | 使用者裝置 |
| 入口 Directory | 有邊幾部機、點去 | 本機設定／個人偏好 | 個人帳戶頁或 launcher |
| 授權 Authorization | 呢個人喺**呢間公司**係乜角色 | 該機自己嘅 DB | 各機本地 |

呢個同本機範圍模型一致：身份／範圍／授權本來就係三件事，跨機只不過把「身份」呢層抽出嚟共用，**範圍同授權仍然留喺本機**。

## 5. 階段方案

### Stage 0 — 現況，零改動
兩組帳號、兩組書籤，或一個靜態入口頁列出兩部機。明確標示「這是另一間公司」。呢個唔丟架，係安全邊界最清楚嘅做法。

### Stage 1 —「Company Passport」（建議，最小可行）
- 每人一對 client keypair／passkey，私鑰留喺自己裝置，唔上雲。
- 每部機各自「註冊呢把公鑰」，並**由該機老闆**授予本地角色；註冊係本機動作，兩機唔使互通。
- 登入時本機驗簽；授權完全讀本機 DB。**冇中央 IdP、冇跨機 session、冇共享 cookie、冇資料同步**。
- 入口：頭像選單 →「我的其他安裝」，列出公司名／地區／網址／真實連線狀態。探測失敗要講失敗，唔好假綠燈（BASE §6）。
- 效果：解鎖一次私鑰，就可以入兩部機；但仍然係**兩次本機授權判斷、兩份資料、兩份審計**。

### Stage 2 —「公司間憑證」（可選，建議先唔做）
若要「集團層摘要」，應該係**非同步、經人批准、有憑證**嘅匯入，沿用 C01 嘅發件箱／Email 單據語意，唔係即時 API。要過法律（C24）、安全、審計三關。唔可以由 UI 拉一個「全部公司」tab 就當做成。

## 6. 本機 UI 點落地（同四張設計稿一致）

- 本機頂欄／左下角**完全唔加公司切換器**（Billy 已拍板一機一公司）。
- 左下角繼續固定「本機公司／滿月堂集團／香港 · 一機一公司」。
- 跨機入口放喺**個人帳戶頁**，唔係全域導覽，避免同 App／Workspace selector 撈亂。
- 每個入口顯示：公司名、地區、網址、連線狀態、「需要另一份授權」。
- 切過去係開新分頁去另一部機，**唔喺同一個 shell 入面換資料**。

## 7. 同本幾「查閱維度」嘅關係（重要）

本機財務頁嘅「全公司／品牌／部門」係**同一部機、同一個 DB** 入面嘅讀取切片；
跨機「全部公司」係**跨 DB、跨法律管轄**嘅事。兩者唔可以共用同一個控件、同一個詞、同一份授權。
一句講完：**本機三視圖屬 Query lens；跨機屬 Tenant boundary，唔係多一個 lens。**

## 10. 總部主機作「登記／批准／入口中心」（2026-11-09 下午，Billy 新指示）

狀態：**設計概念已畫成四張畫面，未經工程決定、未授權施工**。來源：Billy「only Boss and management grade can do this」＋「connect other region machine through the Head office machine」。

### 10.1 先拆「connect」呢個字（重要）

「經總部連接其他地區機」有兩個可能意思，一定要分開：

| 解法 | 內容 | 同 C01／C24／§236 |
|---|---|---|
| (A) 目錄／批准／入口 | 總部記低有邊幾部機、批准登記、提供跳轉入口 | **唔衝突**，純入口層 |
| (B) 即時跨機連線／合併報表 | 總部長期連去地區機撈數 | **直接衝突**，要改決定＋過法律／安全／審計 |

本稿採用 **(A)**。理由：C01 已定兩機冇跨機連線、公司間往來行發件箱；C24 大陸資料留喺大陸機；§236 各有老闆／員工／DB。一個「總部連線」會令「網絡可達」被誤當成「已獲授權」（BASE §9.3），亦會變相做咗中央 IdP／單點外洩。
**一句：統一嘅係「目錄同批准」，唔係「資料庫」。**

### 10.2 三層仍然分開（延續第 4 節）

| 層 | 答嘅問題 | 放喺邊 |
|---|---|---|
| 據點目錄 Directory | 有邊幾部機、係咪已批准、點去 | **總部主機**（今次新增） |
| 身份 Identity | 呢個係咪同一個人 | 使用者自己嘅 key／Passport |
| 授權 Authorization | 呢個人喺**呢部機**係乜角色 | 該機自己嘅 DB |

新增「總部批准」只係喺 Directory 層加一個閘，**唔會**變成 Identity 或 Authorization 嘅來源。總部登記咗一部機，唔代表任何人可以入嗰部機。

### 10.3 權限模型

- **可以新增／批准／撤銷據點**：Boss（owner）＋「管理級」。
- **管理級**係**本機 grant 嘅等級**，唔係一個跨機自動繼承嘅全球角色；同一個人喺深圳機可以係管理級、喺東京機只係 viewer。
- **其他角色**：選單項目由 grant 控制，**直接唔顯示**；就算直接輸入網址，都只見「需要老闆或管理級授權」嘅誠實狀態，唔係一個撳落去冇反應嘅灰色掣。
- 撤銷據點＝移除入口＋標「已撤銷」＋留審計紀錄，**唔刪對方機上任何資料**。

### 10.4 新增據點流程（三步憑證，非同步）

1. **填寫據點資料** — 地區、公司名、機器代號、時區；資料只寫入總部目錄，唔傳去對方。
2. **產生一次性邀請憑證** — 下載 `.json`／複製代碼；有效 72 小時、單次使用；**總部唔會主動連去對方**。
3. **滙入確認檔並批准** — 對方喺自己機滙入邀請、產生含公鑰嘅確認檔；總部上傳、核對指紋、由 Boss／管理級批准 → 目錄新增一列。

全程沿用 C01 發件箱／憑證語意，冇長連線、冇 shared session、冇資料同步。目錄唔顯示「在線／離線」假綠燈（BASE §6）。
